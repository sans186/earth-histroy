## 决策记录

- **R08 呈现形式候选**（未选型）：① 底部"时间带"横向卡片流，按年代排布、可拖拽；② 侧栏"报纸版面"，事件按类别分栏、字号体现重要性；③ 球面"引线标注"，只给当前视口内 3-5 条事件拉引线到地名；④ 右侧"对照表"常驻，不弹卡片，点行展开详情。取舍标准：不遮挡球面主体、可连续浏览不打断。
- **R11 根因**：`polity_names_zh.json` 本身没问题（1900–2000 分片 1713 个政区名 100% 命中）；问题是加载点挂在 `refreshPolities` 里，对照界面在政区图层绘制前打开就拿不到中文名。现已改为 `useGlobeData` 构造时即加载，并加大小写/首尾空格兜底。
- **R16 分析方向**（尚未定位）：拖拽走 `camera.rotate`，每帧触发 `onViewChange` → `onViewSettled` → `paintPolities` 重建实体（signature 相同可跳过，但 fingerprint 仍逐条计算）；另 `requestRenderMode` 未开启，每帧全量重绘。需先加 Performance 采样确认是 CPU 侧重建还是 GPU 侧绘制。
- **R05 战争书目**：glm-4-flash 会编造不存在的文献（如"《美国内战》林肯"），且本机到维基百科不可达，无检索源可校验。不做。翻译类任务（有源文本）另论，R06 已证明可用。
- **R05 事件坐标**：407 条缺坐标的事件抽查后确认为区域型事件（外交关系、贸易网络、气候压力），无单一落点，不强行填补。
- **R05 人物照片**：`images.json` 为空、`images-review.json` 全为 null，缺的是数据源而不是工作量。需先确认图片来源（Wikimedia Commons 是否可达）再谈。
- **R20 底图/瓦片可达性**：OSM 瓦片服务器在本机（大陆网络）整体超时，2D 与 3D 的 standard 底图都只剩纸色；改用 Esri ArcGIS（Topo / Imagery，`{z}/{y}/{x}`，ACAO `*`），配置集中在 `src/config/index.ts` 的 `BASEMAPS`。
- **R20 模型选择**：本机 `ZHIPU_API_KEY_n` 只有 glm-4-flash / glm-4-flash-250414 / glm-4.5-flash 可用（glm-4、glm-4-air、glm-4-plus 均 429「余额不足」）。选 `glm-4-flash-250414`（约 4 s/次、140–200 字）；glm-4.5-flash 会因 reasoning 占满 token 返回空内容。
- **R20 示例污染**：用真实政体（Han → 汉朝）做 few-shot 示例时，模型把示例原文抄进了无关条目（把 11 世纪印度王朝写成汉朝），故示例改为虚构政体并在解析阶段拦截「示例」字样。
- **R20 消歧三件套**：单靠名称，模型会把南印度政权放到苏门答腊。提示里同时给「势力范围中心经纬度」（由政区几何算包围盒中心）+「英文维基条目名」+「`polity_names_zh.json` 的通行中文名」，弁韩/韩国/汉朝这类同名才分得开。
- **R20 遗留风险**：文本为模型生成，长尾条目偶有史实偏差（如把长平之战系于韩国），需要时按 `polity_descriptions.json` 里的 key 单条重跑 `--only=<name>` 覆盖。
- **R23 卡顿根因**：① 窗口 ±20 意味着每次刷新 41 个年份文件，拖动时每 140ms 触发一轮，请求队列直接把开发服务器压满；② `fetchYearFile` 把调用方的 `signal` 直接塞进 `fetch`，而同一年的请求被多个窗口共享——新一轮 abort 上一轮时，共享的 promise 一起 reject，整窗以 AbortError 失败，看起来就是"一直在加载"；③ 每次刷新都登记 blocking 任务，全屏遮罩反复弹出；④ 被取代的加载没有释放 blocking 计数，遮罩可能永久停留。
- **R23 改法**：年份文件请求不再可中止（共享 promise 一定完成并落缓存），只把「等待」包成可中止；拖动期间靠 `timeline.scrubbing` 完全跳过加载，松手后单次加载；首个窗口之后改用非阻塞任务。实测一次跨年拖动（20 步 / 1.5s）：拖动期间 0 个请求，松手后 11 个请求在 143ms 内并发发出；随后 5 年步进只补 7 个新文件，其余命中缓存。
- **R27 来源优先级**：`war_locations.json` 原先那 48 条是模型猜的，抽查发现多条落在海里——太平洋战争在也门（15.3,46.77）、美国独立战争在大西洋（28.0,-61.8）、朝鲜战争在渤海（38.0,117.5）、越南战争在藏南（28.2,93.6）。而 profile 的 `warProcess.phases[].battles[].coords` 是 `[lon, lat]` 数组、来自真实战役记录。因此 `rebuildLocations()` 改为**战役坐标中位数优先**：逐轴取中位数（一场远洋海战拉不动陆战中心），其次才用 `doc.theatreCentroid`，最后保留既有值。94 场里 85 场有战役坐标，其余 9 场（伯罗奔尼撒、亚历山大东征、英国内战、1812 年战争、美墨战争、祖鲁战争、尼日利亚内战、孟加拉国独立战争、乌干达-坦桑尼亚战争）保留模型值并逐条校对，其中亚历山大东征 44.5,34.5、1812 年战争 -79.5,43.0 为手改（模型分别给到阿拉伯内陆与大西洋）。中位数而非均值：太平洋战争 10 场战役横跨 6,000 公里。
