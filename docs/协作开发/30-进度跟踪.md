> 本文件是协作期唯一的「现在做到哪了」总览。详细描述以来源文档为准，这里只存摘要与状态。

> 维护：所有参与者同步更新；项目历史账本见 [REQUIREMENTS.md](../REQUIREMENTS.md)。
> 最后更新：2026-11-18（初稿）

---

## 1. 用途与边界

本文件回答四个问题：

1. 现在有哪些需求与 Bug？
2. 每一条处于什么状态、谁在做？
3. 卡在哪里？
4. 这一轮先做什么？

**写这里：** 编号、类型、标题、状态、优先级、负责人、关联分支 / PR、最近更新、阻塞原因、备注。

**不要写这里：** 完整需求描述、复现步骤、验收标准细节、方案讨论。这些只写在来源文档里，本文件用编号链接过去。

**单一事实来源原则：**

- 详情以来源文档为准；
- 状态、优先级、关联 PR 必须与来源文档一致；
- 两边不一致时，以「最近更新日期更晚」的一边为准，并在同一次提交中修正另一边。

---

## 2. 编号规则

- 直接沿用来源文档的编号：`UR` / `AR` / `UB` / `AB`，本文件**不新造编号**。
- 一行一个编号，不合并、不改号、不复用。
- `Rxx` 是项目历史主账本编号，只读引用；若要跟踪，在本文件加一行并在「来源文档」注明 `REQUIREMENTS.md`。
- 引用其他条目时写全编号，例如「阻塞于 UB-004」。

---

## 3. 状态与优先级

状态定义与来源文档完全一致，不再另立一套：

- 需求（`UR` / `AR`）：待确认 → 已确认 → 开发中 → 待验收 → 已完成；旁路：搁置、已拒绝、重复。
- 缺陷（`UB` / `AB`）：待确认 → 已确认 → 修复中 → 待验证 → 已修复；旁路：无法复现、不修复、重复。

本文件只允许填写上述状态。若来源文档状态已变更，本文件必须同步。

优先级 `P0`–`P3` 的定义见各来源文档第 3 节。本文件中的优先级必须与来源文档一致，调整由主控执行。

### 本轮目标（由主控填写）

| 项目 | 内容 |
|---|---|
| 本轮主题 | 暂无 |
| 开始日期 | - |
| 目标条目 | 暂无 |
| 备注 | 比赛期间以稳定演示为优先，不接大重构 |

### 进行中上限

- 合作者同时进行中的条目不超过 **2** 条；
- 全局同时进行中的 `P0` 条目不超过 **1** 条（避免互相踩踏）；
- 超过上限时，先完成，再开新的。

## 7. 维护约定

1. **登记顺序：** 先写入来源文档，再在同一次提交中追加本文件的一行。反过来不允许。
2. **状态同步：** 任何状态变更，必须在同一次提交中同时更新来源文档与本文件。
3. **开工前必读：** 每次开工先读本文件的「本轮目标」和「总览」，只挑一条「已确认」且无阻塞的条目做。
4. **一次一条：** 不并行开多个分支；做完一条再开下一条。
5. **阻塞要显式：** 卡住时在「阻塞原因」写一句话（例如「等待主控确认验收标准」），并告知主控；不要静默停摆。
6. **完成要可追溯：** 「已完成 / 已修复」行必须能通过 PR 或提交找到改动与验证记录。
7. **不删除行。** 条目作废时状态改为「已拒绝 / 不修复 / 重复 / 无法复现」，保留行与编号。
8. **归档：** 每季度或每个比赛阶段结束时，由主控把已完成的行移到文末「已归档」小节，保留编号与 PR 链接。
9. **对账：** 每次 PR 合并后，主控核对本文件与来源文档是否一致；每周至少一次全量对账。
10. **AI 规则：**
    - 只做本文件中「已确认」且无阻塞的条目；
    - 不得自行新增「已确认」行，新增行一律从「待确认」开始；
    - 不得修改他人条目的标题、优先级、负责人；
    - 完成后必须同时更新来源文档、本文件与汇总数字；
    - 发现新问题先登记到对应文档，不顺手修。
