# 用户发现的 Bug 文档

> 编号前缀 `UB`　｜　本文件记录用户在实际使用中发现的缺陷。
> 状态总览见 [30-进度跟踪.md](./30-进度跟踪.md)；需求见 [10-用户需求.md](./10-用户需求.md)；AI 发现的缺陷见 [21-AI发现的Bug.md](./21-AI发现的Bug.md)。
> 维护：双方均可追加、认领与修复；关闭与标「不修复」需另一方确认。
> 最后更新：2026-11-19（改为双向认领）

---

## 1. 用途与边界

本文件回答：**用户做了什么、看到什么、期望什么、怎样能重复出来。**

**写这里：**

- 页面报错、白屏、卡死、数据不显示；
- 交互行为与预期不一致；
- 中英文文案缺失、错位、截断；
- 数据明显错误（同时按 [CONTRIBUTING.md](../../CONTRIBUTING.md) 的数据勘误口径处理）；
- 性能问题（明确到可观察的现象，如「拖动时卡顿 3 秒」）。

**不要写这里：**

- 想要的新功能（放 [10-用户需求.md](./10-用户需求.md)）；
- 主观喜好但没有可观察差异的意见（可放 `AR` 或直接讨论）；
- 未经验证的猜测性结论（先复现，再记录）；
- 安全问题细节（私下告知主控，不在公开文档写可利用步骤）。

**一条 Bug 一个条目。** 同一根因导致的多个现象写一条，在「实际结果」里列全。

---

## 2. 编号规则

- 从 `UB-001` 开始，三位数字，全局递增，**永不复用**。
- 示例条目固定使用 `UB-000`，不计入正式编号。
- 引用写全编号（如 `UB-007`）。
- 与 `UR`、`AR`、`AB` 编号互不共用。
- 关闭后编号保留，不因修复而删除或改号。

## 3. 状态与优先级

### 状态定义

| 状态 | 含义 |
|---|---|
| 待确认 | 已记录，尚未复现或未判断是否为缺陷 |
| 已确认 | 已复现，确认是缺陷，等待认领 |
| 已认领 | 已确定修复人，尚未开工 |
| 修复中 | 已建分支，负责人正在修 |
| 待验证 | 修复已提交 PR，等待验证 |
| 已修复 | 验证通过并合并进 `main` |
| 无法复现 | 按当前步骤无法重复，需补充信息 |
| 不修复 | 确认存在但不修，必须写理由 |
| 重复 | 与已有条目重复，必须指向原编号 |

### 状态流转

```text
待确认 ──> 已确认 ──> 已认领 ──> 修复中 ──> 待验证 ──> 已修复
   │          │          │          │          │
   │          │          │          │          └──> 修复中（验证不通过）
   │          │          │          └──> 已确认（放弃当前修法）
   │          │          └──> 已确认（放弃认领）
   │          └──> 不修复（写理由）
   ├──> 无法复现（补充信息后可回到待确认）
   └──> 重复（终态，指向原编号）
```

规则：

1. 「待验证」必须附 PR 链接与自查结果。
2. 「已修复」必须附验证人、验证日期与验证方式；不能只写「修好了」。
3. 「无法复现」要写清楚尝试过的环境与步骤；用户补充信息后可重新打开。
4. 「不修复」必须写理由（例如移动端未适配、上游数据限制、成本高于收益）。
5. 「已认领」必须填负责人（人的姓名）、认领日期与认领方式（自领 / 转派 / 代领）；本文件、30、PR assignee 三处缺一不算认领。
6. 转派先取得现负责人同意，再写「负责人变更记录」；放弃认领回到「已确认」并释放负责人。
7. 同一编号同时只能有一位负责人；同时认领以认领日期较早者为准。

### 优先级

| 优先级 | 判定标准 | 处理节奏 |
|---|---|---|
| P0 | 页面不可用、数据损坏或丢失、安全风险、演示阻断 | 当天处理 |
| P1 | 核心功能错误，有明确用户影响 | 本迭代内 |
| P2 | 一般功能缺陷或明显体验问题 | 排期修复 |
| P3 | 轻微显示问题、低频场景 | 空闲时修复 |

优先级由双方协商确定，分歧由用户拍板。提交时可以给建议值。

## 4. 字段说明

| 字段 | 必填 | 说明 |
|---|---|---|
| 编号 | 是 | `UB-xxx` |
| 标题 | 是 | 一句话描述现象，不超过 30 字 |
| 状态 | 是 | 取值见第 3 节 |
| 优先级 | 是 | `P0`–`P3`，未定时填「待定」 |
| 发现人 / 来源 | 是 | 谁、通过什么渠道、什么日期 |
| 发现日期 | 是 | `YYYY-MM-DD` |
| 更新日期 | 是 | 最近修改日期 |
| 环境 | 是 | 浏览器与版本、操作系统、设备、代码版本（提交号或分支） |
| 复现步骤 | 是 | 编号步骤，别人照着能重复 |
| 期望结果 | 是 | 正确行为应该是什么 |
| 实际结果 | 是 | 实际发生了什么，包含报错文本 |
| 出现频率 | 是 | 每次 / 偶尔 / 仅一次；偶尔出现时写触发条件 |
| 影响范围 | 否 | 影响哪些功能、哪些用户、是否有数据风险 |
| 证据 | 否 | 截图、录屏、控制台报错、错误横幅的诊断信息 |
| 关联条目 | 否 | 相关需求 / Bug 编号 |
| 关联分支 / PR / 提交 | 否 | 修复时填写 |
| 负责人 | 是 | 认领后必填，写人的姓名（不写 AI 名称）；未认领填「未分配」 |
| 认领日期 | 是 | 认领或转派当天，`YYYY-MM-DD` |
| 认领方式 | 是 | 自领 / 转派 / 代领（代领需注明被代的人） |
| 负责人变更记录 | 否 | 每次换人或释放一行：日期、原负责人 → 新负责人、原因 |
| 改动范围 | 否 | 认领时填写：要动的文件 / 模块，用于防撞车 |
| 根因 | 否 | 定位后填写 |
| 修复说明 | 否 | 改了什么，为什么这样改 |
| 验证记录 | 否 | 验证人、日期、方式、结果 |
| 备注 | 否 | 补充说明、变更记录 |

## 7. 维护约定

1. **先复现，再定性。** 不能复现的标「无法复现」，不要猜根因。
2. **步骤可执行。** 每一步都写具体操作与可见状态，不写「打开页面随便点几下」。
3. **证据脱敏。** 截图和日志里不能出现 token、内网地址、个人信息。
4. **只改允许改的字段。** 状态、认领信息、负责人变更记录、优先级（协商）、根因、修复说明、验证记录、关联字段可更新；现象描述原文不改，补充写在「备注」。
5. **与进度跟踪同步。** 新增与状态变更在同一次提交中更新 [30-进度跟踪.md](./30-进度跟踪.md)。
6. **不删除条目。** 重复的指向原编号；不修的保留并写理由。
7. **AI 规则：**
   - 先按步骤复现，再改状态；不能复现时不得标「已确认」；
   - 只能修本文件中负责人为本方、状态为「已认领 / 修复中」的条目；
   - 一次只修一个条目，不顺手重构无关代码；
   - 修复后必须提供可复现的验证结果；
   - 涉及数据、许可、依赖、部署的问题，先报告主控。
