> 仓库：<https://github.com/sans186/earth-histroy>　｜　主分支：`main`　｜　唯一远端：`origin`

## 0. 先看这一页

这个仓库是一个纯静态的 3D 历史地图网站（Vue 3 + TypeScript + CesiumJS + MapLibre），没有后端、没有数据库。项目正在参加 2026 Trae 好应用大赏赛。

**你不需要会编程，也不需要手敲 Git。** 你的 AI 助手照着本手册执行，你负责三件事：

1. 说清楚想要什么（需求）或哪里不对（Bug）；
2. 验收结果；
3. 决定做不做、先做哪个。

### 三条铁律

1. **不直接改 `main`。** 所有改动走「分支 + 合并请求（PR）」，由主控合并。
2. **不提交密钥和大文件。** `.env`、`dist/`、`node_modules/`、`data/` 都不进提交；`public/` 下的批量数据不手工改动，只能通过 `scripts/` 生成。
3. **改完必须自查。** 至少跑 `npm run typecheck` 和 `npm run build`，并把命令与结果写进 PR。没有验证结果的交付视为未完成。

### 给 AI 助手的开工提示词（可直接复制）

```text
你在 Earth 仓库工作。开工前先读：
1. docs/协作开发/00-合作手册.md
2. CONTRIBUTING.md
3. docs/协作开发/30-进度跟踪.md

遵守以下约束：
- 不直接改 main，不 force push，不用 reset --hard 改共享分支；
- 不提交 .env、dist、node_modules、data、备份文件；
- 不手改 public/ 下的批量数据，不加新依赖，不使用 emoji；
- 一次只做进度跟踪里一条「已确认」的条目；
- 开工前切到 main 并 pull，结束时跑 typecheck 与 build；
- 完成后同步更新来源文档和进度跟踪，输出 PR 链接与验证结果；
- 遇到冲突、需求不清或连续两次失败，停下来报告，不要扩大改动范围。
```

## 1. 项目是什么

把 18,000 条历史事件、96 场战争、418 位人物，钉在一颗可以按年份拖动的 3D 地球上。拖动时间轴，公元前 3200 年到 2026 年的政区边界、历史事件、人物足迹与战争会跟着重绘。数据按年份切片，浏览器用到哪一年才取哪一年。

它**不是**史料数据库，不是学术工具，也不是对外生产服务。数据含 AI 生成内容，不保证史实准确。完整定位与免责见 [README.md](../../README.md) 与 [开源说明.md](../开源说明.md)。

比赛期间的目标很具体：**稳定演示、可控改动、每个改动都能解释和回退。** 不做大重构，不做无来源的数据扩写。

## 2. 角色与分工

| 角色 | 负责 | 不负责 |
|---|---|---|
| 主控（仓库所有者） | 合并 `main`、发布部署、确定优先级与数据口径、处理冲突、批准新依赖 | 不替你写需求和验收标准 |

权限前提：主控需在 GitHub 上把你加为仓库协作者（Write 权限）。若暂时只有只读权限，则先 Fork，再从 Fork 发 PR，流程其余部分相同。

## 3. 目录与代码组织

```
Earth/
├── index.html                 # 页面入口
├── vite.config.js             # 构建配置：Cesium 静态拷贝、gzip、产物裁剪
├── package.json               # 命令与依赖
├── src/                       # 源码
│   ├── App.vue                # 布局与全局编排
│   ├── main.ts                # 应用入口
│   ├── components/            # 界面组件（卡片、面板、地图舞台等）
│   ├── composables/           # 组合式逻辑（useGlobeData）
│   ├── services/              # 命令式服务：3D、2D、数据请求、战争数据
│   ├── stores/                # Pinia 状态（ui / timeline / layers / people / wars）
│   ├── lib/                   # 纯函数与工具（i18n、格式化、地理、对照、错误）
│   ├── config/index.ts        # 年份范围、底图、路径、阈值、网络参数
│   ├── types/index.ts         # 共享数据模型
│   └── styles/                # tokens.css + base.css
├── public/                    # 随包静态数据（事件、政区、人物、战争、国界）
├── scripts/                   # 数据流水线与校验脚本
├── docs/                      # 文档
│   └── 协作开发/              # 本手册与五份协作账本
├── design/                    # 视觉原型（单 HTML）
└── dist/                      # 构建产物（不入库）
```

### 改哪里，看这张表

| 想改的东西 | 去哪里 | 注意 |
|---|---|---|
| 界面布局、卡片、面板 | `src/components/*.vue` | 先看同名组件的现有写法 |
| 全局状态 | `src/stores/*.ts` | 不要复制已有状态 |
| 数据加载与请求 | `src/services/data.ts`、`http.ts` | 所有请求走统一请求层，不要新写裸 `fetch` |
| 3D / 2D 渲染 | `src/services/globe.ts`、`map2d.ts` | 高风险区，改动前先说明 |
| 年份、底图、阈值等配置 | `src/config/index.ts` | 公共文件，改动前先在群里说 |
| 界面文案与中英文 | `src/lib/i18n.ts` | 中英两份都要补 |
| 通用工具函数 | `src/lib/*.ts` | 优先复用，不重复造 |
| 数据类型 | `src/types/index.ts` | 公共文件，改动可能影响多处 |
| 数据资产 | `public/` | 禁止手改，必须通过 `scripts/` 生成并校验 |
| 数据脚本 | `scripts/` | 先读 [scripts/README.md](../../scripts/README.md) |
| 文档 | `docs/` | 需求与 Bug 写入 `docs/协作开发/` |

### 两条架构红线

1. **Cesium / MapLibre 的实例和实体，绝不放进 Vue 的 `ref()` / `reactive()`。** 它们由 `src/services/` 命令式管理，交给响应式代理会导致性能雪崩或运行时异常。
2. **用户可见文案必须走 `src/lib/i18n.ts`，中英文同时补齐。** 不要把中文硬编码进组件。

## 4. 把仓库跑起来

### 环境

- Node.js 20 或更高的 LTS（开发环境为 v22.22.2）
- npm（开发环境为 10.9.7）
- Git
- 现代浏览器（Chrome / Edge）
- 不需要数据库、不需要后端、不需要服务端密钥

### 首次

```bash
git clone https://github.com/sans186/earth-histroy.git
cd earth-histroy
npm ci
npm run dev
```

打开 <http://localhost:3000>。端口被占用时 Vite 会自动换端口；也可指定：

```bash
npm run dev -- --port 3005 --strictPort
```

### 常用命令

| 命令 | 用途 |
|---|---|
| `npm run dev` | 本地开发（端口 3000） |
| `npm run build` | 生产构建；构建前会自动校验数据，不通过则中止 |
| `npm run preview` | 预览 `dist/` 产物 |
| `npm run typecheck` | TypeScript 类型检查 |
| `npm run validate:data` | 全量校验数据资产 |
| `npm run audit:profiles` | 审计战争 / 人物档案完整度 |
| `npm run verify:smoke` | 故障注入冒烟（需构建产物与 Chromium 系浏览器） |

### 常见问题

- **首次启动很慢**：Vite 要预构建依赖，并把 Cesium 静态资源拷到 `public/`，属正常现象。
- **`public/` 有一万多个文件**：dev server 的文件监听已刻意限定在 `src/`。不要把监听范围改大，否则 Windows 上会卡死。
- **没有 `.env` 也能开发**：只有翻译、内容生成类脚本需要模型凭据。需要时向主控要，不要把密钥提交进仓库。
- **构建时清理 `dist` 失败**：先确认不是杀毒软件或 Windows 文件占用；不要为了绕过而删除源码或构建配置，把完整报错交给主控。
- **不要随手 `npm install <包名>`**：新依赖需要主控批准，否则会改动 `package-lock.json` 并与其他人的改动冲突。

## 5. Git 最小必要流程

合作者不需要手敲这些命令，由 AI 助手执行。每一步失败都先停下报告，不要连续重试或换一种破坏性做法。

### 5.1 一次性准备

```bash
git clone https://github.com/sans186/earth-histroy.git
cd earth-histroy
git config user.name "你的名字"
git config user.email "你的邮箱"
```

首次推送需要 GitHub 凭据（浏览器登录或 Personal Access Token）。**不要把 token 写进任何文件或提交。**

### 5.2 每次开工

```bash
git switch main
git pull --ff-only
git status
```

工作区必须是干净的，或只剩你明确知道的改动。看到不认识的改动，先停下问主控。

### 5.3 建分支

```bash
git switch -c feat/compare-swap
```

分支命名：`类型/简短英文描述`，全小写、连字符分隔，不使用中文。

| 前缀 | 用途 | 例子 |
|---|---|---|
| `feat/` | 新功能 | `feat/event-filter` |
| `fix/` | 修 Bug | `fix/timeline-drag` |
| `docs/` | 只改文档 | `docs/collab-handbook` |
| `data/` | 数据修正（需附来源） | `data/dan-dong-fix` |

一个分支只做一件事。分支存活尽量不超过两天。

### 5.4 提交

```bash
git status
git add src/components/CompareBoard.vue
git commit -m "feat(compare): 增加 A/B 列一键交换"
```

提交信息格式：`类型(范围): 一句话说明`。

| 类型 | 用途 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修复缺陷 |
| `docs` | 文档 |
| `data` | 数据修正（提交信息里写来源） |
| `refactor` | 不改变行为的重构（比赛期尽量少做） |
| `chore` | 构建、依赖、脚本等杂项 |

要求：

- 一条提交一件事，不要把代码、数据、格式化混在一起。
- 不提交未使用的文件、日志、备份、截图原图。
- 提交前 `git status` 确认没有 `.env`、`dist/`、`node_modules/`、`data/`、`*.backup_*`。

### 5.5 推送

```bash
git push -u origin feat/compare-swap
```

只推自己的分支。**永远不要推 `main`，永远不要 `--force`。**

### 5.6 发起合并请求（PR）

有 GitHub CLI：

```bash
gh pr create --base main --head feat/compare-swap --title "feat(compare): 增加 A/B 列一键交换" --body "关联：UR-003。改动：... 验证：... 风险：..."
```

> 上面是单行命令，PowerShell 与 Git Bash 都可直接执行。不要把命令拆成多行加反斜杠，PowerShell 的续行符不是反斜杠。

没有 CLI：打开

```text
https://github.com/sans186/earth-histroy/compare/main...feat/compare-swap
```

点击「Create pull request」。

PR 描述必须包含：

1. 关联编号（`UR-xxx` / `AR-xxx` / `UB-xxx` / `AB-xxx`）；
2. 改了什么、为什么改；
3. 怎么验证：执行的命令、结果、必要的截图或录屏；
4. 已知限制与风险；
5. 需要主控决策的点（如果有）。

### 5.7 合并之后

由主控合并（建议 Squash merge，保持 `main` 历史线性）。合并后你执行：

```bash
git switch main
git pull --ff-only
git branch -d feat/compare-swap
```

不要自行合并 PR，不要自行删除远端分支。

### 5.8 分支落后于 main

```bash
git switch main
git pull --ff-only
git switch feat/compare-swap
git merge main
```

解决冲突后正常提交、推送。**不要用 `rebase` + `push --force`。**

### 5.9 出问题时可以看的命令

```bash
git status                  # 当前改了什么
git log --oneline -10       # 最近提交
git diff                    # 未暂存的改动
git diff --staged           # 已暂存的改动
git branch -vv              # 本地分支与远端关系
```

## 6. 如何避免和别人冲突

冲突的根源是「同一个人改同一个文件的同一块」。按下面的规则可以把冲突降到接近零。

1. **每天开工先 `pull`。** 不要在一周前的代码上开工。
2. **一人一分支，一件事一分支。** 分支越短，冲突越少。
3. **动手前先说。** 在协作群里写一句「我今天改对照界面」，避免两人同时改同一块。
4. **公共文件先协调。** 以下文件改动前必须在群里说，并由一人负责：
   - `package.json`、`package-lock.json`
   - `vite.config.js`、`tsconfig.json`、`eslint.config.js`
   - `src/App.vue`、`src/config/index.ts`、`src/types/index.ts`
   - `src/lib/i18n.ts`、`src/styles/tokens.css`
   - `docs/REQUIREMENTS.md`、`docs/协作开发/30-进度跟踪.md`
   - `LICENSE`、`NOTICE`
5. **不做顺手重构。** 不重排 import、不整文件格式化、不改无关缩进。否则你的 diff 会覆盖别人的改动。
6. **不手改 `public/` 批量数据。** 一万多个文件，手改既易错又会造成巨大冲突；用 `scripts/` 生成。
7. **不新增依赖。** `package-lock.json` 是冲突重灾区。
8. **文档追加而不是重写。** 进度跟踪只追加自己的行或更新自己条目的字段。

### 冲突处理协议

1. 停下。不要 `push --force`，不要 `reset --hard`，不要删分支。
2. 执行 5.8 的合并流程。
3. 一次解决一个文件。冲突标记 `<<<<<<<` / `=======` / `>>>>>>>` 必须全部清除。
4. `package-lock.json` 冲突：不要手工编辑，先询问主控，由主控决定用哪一版并重新 `npm install`。
5. 解决后跑完整自查，再提交合并结果。
6. 不确定就 `git merge --abort`，恢复原状后报告。

## 7. 改完之后怎么自查

### 必跑项

| 检查 | 命令 | 何时必须 | 通过标准 |
|---|---|---|---|
| 类型检查 | `npm run typecheck` | 任何代码改动 | 退出码 0，无报错 |
| 生产构建 | `npm run build` | 任何代码 / 数据改动 | 构建成功（构建前会自动校验数据） |
| 数据校验 | `npm run validate:data` | 改了 `public/` 或 `scripts/` | ERROR 0 / WARNING 0 |
| 档案审计 | `npm run audit:profiles` | 改了人物 / 战争档案 | 对应档案全部通过，孤儿 0 |
| 故障冒烟 | `npm run verify:smoke` | 改了请求层、错误提示、加载逻辑 | 全部用例通过 |

### 手工验收清单

只在桌面端验证（项目未适配移动端）：

- [ ] `npm run dev` 能打开，页面无白屏；
- [ ] 3D 地球与 2D 地图都能切换，底图正常；
- [ ] 时间轴可拖动，`-5 / -1 / +1 / +5` 与输入框跳年正常；
- [ ] 事件卡片、政区卡片、人物卡片、战争卡片能打开并关闭；
- [ ] 中英文切换后，新增文案两种语言都正确；
- [ ] 浏览器控制台没有新增报错；
- [ ] 断网或接口失败时，错误横幅能出现且「重试」有效（改了加载逻辑时必测）。

### 交付前最后一眼

```bash
git status
git diff --stat
```

确认：只改了预期的文件；没有密钥、产物、日志、备份；没有把无关格式化带进来。

## 8. 怎样提需求

需求写进 [10-用户需求.md](./10-用户需求.md)。你不需要填表格，直接对 AI 说：

```text
请把这条记到用户需求文档：
我想要（在哪个界面）做（什么事），因为（解决什么问题）。
做到（什么程度）就算完成。
我觉得优先级是（高 / 中 / 低）。
```

AI 负责把它拆成规范的字段和可观察的验收标准。一条需求只写一件事。

好需求与坏需求的区别：

| 坏 | 好 |
|---|---|
| 「界面再好看点」 | 「事件卡片正文最小字号提高到 14px，左侧介绍卡片不再需要放大才能读」 |
| 「加个搜索」 | 「按 Ctrl+K 打开搜索框，输入中文或英文名称能定位到事件/人物/战争，回车跳转」 |
| 「优化一下性能」 | 「拖动时间轴时不再出现全屏加载遮罩，松手后 1 秒内完成加载」 |

写需求时不要指定技术方案（例如「用 Redis 缓存」）。方案由实现者提，主控决定。

**AI 规则：登记需求不等于开工。** 只有状态到「已确认」或「开发中」的条目才能动代码。需求范围不清时，写进「待确认问题」，不要自行补全。

## 9. 怎样报 Bug

Bug 写进 [20-用户发现的Bug.md](./20-用户发现的Bug.md)。直接对 AI 说：

```text
请把这条记到用户发现的 Bug 文档：
我做了（什么操作），看到（什么现象），期望是（什么）。
浏览器是（Chrome / Edge / 版本），能否重复：（每次都出现 / 偶尔 / 只出现一次）。
截图或报错在（路径 / 粘贴内容）。
```

一条 Bug 一个条目。复现步骤要能让别人照着做出来：

```text
1. 打开首页，等待地球加载完成；
2. 把时间轴拖到公元前 500 年；
3. 打开右侧第一条事件卡片；
4. 点击卡片右上角关闭按钮。
```

期望：卡片关闭，地图保持当前年份。
实际：卡片关闭后时间轴跳回 2026 年。

证据优先级：录屏 > 截图 > 文字描述。控制台报错和错误横幅里的「复制诊断信息」很有用，但**粘贴前确认不含个人信息或密钥**。

安全问题（例如能读到别人的数据、密钥泄露）不要写进公开文档，直接私下告知主控。

**AI 规则：先复现再定性。** 不能复现就标「无法复现」并写清楚尝试过什么；不要顺手修无关问题；不要为了让报告好看而夸大影响。

## 10. 代码与命名规范

### 格式

沿用仓库根目录 [.prettierrc](../../.prettierrc)：

- 2 空格缩进；
- 单引号；
- 语句结尾带分号；
- 行宽 100；
- 尾随逗号；
- 换行符 LF。

### 硬性规则

- **禁止 emoji**：代码、注释、文档、提交信息、PR 描述都不要用（见 [CLAUDE.md](../../CLAUDE.md)）。
- **Vue 组件**使用 `<script setup lang="ts">` + Composition API，不写 Options API。
- **TypeScript**：不用 `any` 兜底；不用 `@ts-ignore` / `@ts-expect-error` 压错误；类型不确定就先查 `src/types/index.ts`。
- **文案**：界面文字全部走 `src/lib/i18n.ts`，中英文同时补齐。
- **请求**：统一走 `src/services/http.ts`，不要在组件里直接 `fetch`。
- **错误**：沿用 `AppError` / `ErrorNotice` 机制，不要新造一套提示。
- **样式**：优先使用 `src/styles/tokens.css` 里的 CSS 变量，不硬编码颜色和字号。
- **注释**：用中文，只解释「为什么」，不复述代码；不写无信息量的注释。

### 命名

| 对象 | 规则 | 例子 |
|---|---|---|
| Vue 组件文件 | PascalCase | `EventCard.vue` |
| 组合式函数 | `use` + PascalCase，camelCase 文件名 | `useGlobeData.ts` |
| 服务 / store / 工具 | camelCase 文件名 | `war-data.ts`、`timeline.ts` |
| 类型 / 接口 | PascalCase | `TimelineState` |
| 函数 / 变量 | camelCase | `loadYearEvents` |
| 常量 | UPPER_SNAKE_CASE | `YEAR_WINDOW` |
| CSS 变量 | `--kebab-case` | `--fs-body` |
| 分支 | 类型/英文短描述 | `fix/card-close` |
| 数据 / 文档编号 | 见各文档的编号规则 | `UR-001`、`UB-007` |

### 改动纪律

- 只改与当前条目相关的代码；不顺手重构、不整文件格式化。
- 不删除看起来「没用」的代码，除非能确认无引用；不确定就问。
- 不新增依赖；确需新增时，先在进度跟踪里写理由，由主控批准。
- 数据改动遵循 [CONTRIBUTING.md](../../CONTRIBUTING.md)：一条改动一件事，附来源，同步 `docs/ai-generated-fields.json`。

## 11. 明确禁止的操作

| 禁止 | 原因 | 正确做法 |
|---|---|---|
| `git push --force` / `-f`，尤其对 `main` | 覆盖他人提交，可能永久丢失工作 | 用普通 push；冲突按第 6 节处理 |
| `git reset --hard` 改共享分支 | 同上 | 需要撤销时新建提交或询问主控 |
| 直接向 `main` 提交或推送 | 绕过评审，破坏可回退性 | 分支 + PR |
| 删除远端分支 / 改写历史 | 影响他人协作 | 由主控处理 |
| 提交 `.env`、token、密钥、服务器信息 | 泄露凭据 | 用 `.env.example` 说明变量名；密钥私下传递 |
| 提交 `dist/`、`node_modules/`、`data/`、`*.backup_*`、日志 | 体积大、不可维护 | 已在 `.gitignore`，不要强行 `git add -f` |
| 手改 `public/` 批量数据 | 一万多个文件，易错且冲突巨大 | 改 `scripts/` 生成并跑 `validate:data` |
| 用大模型批量重写人物评价、战争叙述或整份数据集 | 违反项目数据口径，难以核验 | 按 `CONTRIBUTING.md` 做单条、带来源的修正 |
| 删除或改写许可与署名（`LICENSE`、`NOTICE`、README 的数据来源） | 违反上游许可 | 保持原样；需要调整先问主控 |
| 修改 `docs/REQUIREMENTS.md` | 项目主账本，由主控维护 | 在协作文档登记，由主控决定是否并入 |
| 新增依赖、改 `package.json` | 影响全体协作与构建 | 先申请，由主控批准 |
| 执行部署（`npm run deploy:cf`、改域名、动 Cloudflare 配置） | 影响线上演示 | 只由主控执行 |
| 运行会批量改数据的脚本（`repair:data`、`simplify:polities` 等） | 可能大范围改写数据 | 先用试运行 / 只读模式确认影响，再经主控批准；没有 dry-run 的脚本不要直接跑 |
| 在代码、文档、提交信息中使用 emoji | 项目硬性规定 | 用文字表达 |
| 改 `.git/` 内部文件、改 remote 地址 | 破坏仓库完整性 | 需要时由主控操作 |

### 不要改动的目录与文件

除上表列出的操作外，以下位置一律不要手工修改：

- `node_modules/`：依赖安装产物，改了就丢；
- `dist/`、`dist.stale-*`、`dist__stale/`：构建产物与历史快照；
- `data/`：本地原始数据，不入库；
- `public/` 下的批量数据：必须通过 `scripts/` 生成并校验；
- `.git/`：仓库内部数据；
- `.wrangler/`、`.cloudflare/`、`deploy/` 中的部署配置：只由主控维护；
- `.archive/`、`.omo/`、`.workbuddy/`、`.playwright-cli/`、`.tmp-*`：本地工作目录，不入库；
- `scripts/.backups/`、`*.backup_*`、`*_backup.*`：备份文件，不入库；
- `.env`、`.dev.vars` 及任何含密钥的文件；
- `LICENSE`、`NOTICE`、`docs/REQUIREMENTS.md`：许可与主账本，只由主控维护。

## 12. 交付时该给对方什么信息

交付不是「改好了」三个字。每次交付（PR 描述或群消息）必须包含：

1. **关联编号**：`UR-003` / `UB-007` 等；
2. **分支名与 PR 链接**；
3. **改了什么**：文件列表 + 一句话说明每个文件的改动；
4. **为什么这么改**：根因或设计取舍；
5. **怎么验证**：
   - 执行的命令与结果（`typecheck` 退出码、`build` 是否通过、`validate:data` 计数）；
   - 手工验收步骤；
   - 界面改动附截图或录屏（改前 / 改后）；
6. **已知限制**：没做的、没测的、可能受影响的场景；
7. **需要对方决策的点**：有就写，没有就写「无」；
8. **回退方式**：例如「revert 这个 PR 即可，无数据迁移」。

示例：

```text
关联：UR-003（对照界面一键交换 A/B）
分支：feat/compare-swap
改动：CompareBoard.vue 增加交换按钮与状态互换逻辑；i18n.ts 补中英文案
验证：npm run typecheck 退出码 0；npm run build 通过；Chrome 手工验证 3D/2D 各一次
截图：见 PR 附件
限制：只在桌面端验证；未处理两列都为空的情况（按钮置灰）
需要决策：无
回退：revert 本 PR 即可，无数据变更
```

## 13. 卡住了怎么办

按顺序处理：

1. **需求不清**：在进度跟踪对应行写「阻塞原因：需求范围待确认」，然后问主控。不要猜。
2. **Git 冲突**：按第 6 节协议；不确定就 `git merge --abort` 恢复后报告。
3. **检查连续两次失败**：停止重试，把完整报错、执行过的命令、当前 `git status` 发给主控。
4. **发现问题超出当前条目**：不要顺手修。登记到对应的需求或 Bug 文档，继续当前任务或停下等排期。
5. **涉及数据、许可、部署、依赖**：一律先问主控。
