# 用户需求文档

> 编号前缀 `UR`　｜　本文件记录「用户想要什么」，不记录实现方案。
> 状态总览见 [30-进度跟踪.md](./30-进度跟踪.md)；缺陷见 [20-用户发现的Bug.md](./20-用户发现的Bug.md) 与 [21-AI发现的Bug.md](./21-AI发现的Bug.md)。
> 维护：合作者与其 AI 可追加；改号、删除、调整优先级需主控确认。
> 最后更新：2026-11-18（初稿）

---

## 1. 用途与边界

本文件回答三个问题：**谁**在**什么场景**下，想要**什么结果**。

**写这里：**

- 来自用户口述、截图、演示反馈的功能期望与体验改进；
- 对内容、文案、交互方式的要求；
- 明确的「不做」边界，避免实现时扩大范围。

**不要写这里：**

- 技术实现方案（放到 [11-AI建议需求.md](./11-AI建议需求.md) 或 PR 描述）；
- 缺陷与异常（放到用户 Bug 文档）；
- 未经用户确认的 AI 推测（放到 AI 建议需求文档）；
- 项目历史需求 `R01–R37`（已在 [REQUIREMENTS.md](../REQUIREMENTS.md) 登记，本文件不复制）。

**粒度：** 一条需求只描述一件事。像「优化对照界面」这种包含多个改动的，拆成多条。

## 2. 编号规则

- 从 `UR-001` 开始，三位数字，全局递增，**永不复用**。
- 编号一旦分配，不因标题修改而改变；作废条目标「已拒绝 / 重复」，保留编号。
- 示例条目固定使用 `UR-000`，不计入正式编号，不参与统计。
- 引用时必须写全编号（如 `UR-012`），不要写「第 12 条」。
- 若主控决定并入项目主账本，在条目「主账本编号」字段回填 `Rxx`；`UR` 编号继续保留，便于追溯。
- 不同文档的编号互不共用：`UR` 与 `AR`、`UB`、`AB` 各自独立。

## 3. 状态与优先级

### 状态定义

| 状态 | 含义 |
|---|---|
| 待确认 | 已记录，范围、优先级、是否要做尚未确定 |
| 已确认 | 主控确认要做，优先级已定，可以排期 |
| 开发中 | 已建分支，有人正在实现 |
| 待验收 | PR 已提交且自查通过，等待主控验收 |
| 已完成 | 主控验收通过，已合并进 `main` |
| 搁置 | 确认有价值，但当前阶段不做 |
| 已拒绝 | 决定不做，必须写明理由 |
| 重复 | 与已有条目重复，必须指向原编号 |

### 状态流转

```text
待确认 ──> 已确认 ──> 开发中 ──> 待验收 ──> 已完成
   │          │          │          │
   │          │          │          └──> 开发中（验收不通过）
   │          │          └──> 搁置 ──> 已确认
   │          └──> 搁置
   ├──> 已拒绝（终态，写理由）
   └──> 重复（终态，指向原编号）
```

规则：

1. 不得跳过「待验收」直接标「已完成」。
2. 每次状态变更都必须更新「更新日期」。
3. 标「已完成」必须填写关联 PR / 提交与验收记录。
4. 「已拒绝」「重复」「已完成」为终态；确需重启，新建条目并在备注里指向旧编号。

### 优先级

| 优先级 | 判定标准 | 处理节奏 |
|---|---|---|
| P0 | 阻断演示、核心流程不可用、数据损坏或安全风险 | 当天处理 |
| P1 | 核心功能受损，有明确用户影响 | 本迭代内 |
| P2 | 明确的体验改进或内容补充 | 排期做 |
| P3 | 想法、锦上添花、可选优化 | 空闲时做 |

优先级由主控最终确定。提出者可以给建议值，但不要自行上调。

## 4. 字段说明

| 字段 | 必填 | 说明 |
|---|---|---|
| 编号 | 是 | `UR-xxx`，按第 2 节规则分配 |
| 标题 | 是 | 一句话说清要什么，不超过 30 字 |
| 状态 | 是 | 取值见第 3 节 |
| 优先级 | 是 | `P0`–`P3`，未定时填「待定」 |
| 来源 | 是 | 提出人 + 渠道 + 日期，例如「用户，2026-11-18 对话口述」 |
| 提出日期 | 是 | `YYYY-MM-DD` |
| 更新日期 | 是 | 最近一次修改状态的日期 |
| 目标用户与场景 | 是 | 谁在什么情况下会遇到这个问题 |
| 需求描述 | 是 | 希望发生什么，用用户能理解的语言，不写技术方案 |
| 验收标准 | 是 | 可观察、可复现的完成条件，逐条列出 |
| 边界（不做什么） | 否 | 明确排除的范围，防止实现时扩大 |
| 主账本编号 | 否 | 若并入 [REQUIREMENTS.md](../REQUIREMENTS.md)，填 `Rxx` |
| 关联条目 | 否 | 相关需求 / Bug 编号，如 `UB-004` |
| 关联分支 / PR / 提交 | 否 | 开发中之后填写 |
| 负责人 | 否 | 实现者；未分配时留空 |
| 待确认问题 | 否 | 范围不清时列出，由主控回答 |
| 备注 / 决策 | 否 | 取舍理由、变更记录 |

## 7. 维护约定

1. **追加不覆盖。** 新条目追加到索引表和条目详情末尾；不重排、不改写他人条目。
2. **只改允许改的字段。** 状态、关联分支 / PR / 提交、更新日期、负责人可随进展修改；需求描述原文不改，补充写在「备注」。
3. **优先级由主控调整。** 提出者可以给建议值。
4. **每条至少一个验收标准。** 写不出可观察标准的，状态先保持「待确认」，并把问题写进「待确认问题」。
5. **与进度跟踪同步。** 新增、改状态、完成，都必须在同一次提交中更新 [30-进度跟踪.md](./30-进度跟踪.md)。
6. **不删除条目。** 作废标「已拒绝 / 重复」；需要归档时移到文末「已归档」小节，保留编号。
7. **AI 规则：**
   - 可以代用户登记需求，但不得在状态未到「已确认 / 开发中」时动代码；
   - 不得自行提升优先级或缩小验收标准；
   - 不得把 AI 自己的方案写成用户的原始需求，方案放 `AR` 文档；
   - 范围不清时保留「待确认」，向主控提问，不猜测补全。
