# AI 发现的 Bug 文档

> 编号前缀 `AB`　｜　本文件记录 AI 通过读代码、跑命令、审计脚本发现的缺陷。
> 状态总览见 [30-进度跟踪.md](./30-进度跟踪.md)；用户发现的缺陷见 [20-用户发现的Bug.md](./20-用户发现的Bug.md)；AI 的改进建议见 [11-AI建议需求.md](./11-AI建议需求.md)。
> 维护：AI 可追加；确认、修复、关闭由主控决定。
> 最后更新：2026-11-18（登记 AB-001、AB-002）

## 1. 用途与边界

本文件回答：**AI 在哪里看到了一段会出错、会退化或与文档不符的代码，证据是什么。**

**写这里：**

- 静态阅读发现的可验证缺陷（空值、越界、竞态、错误处理缺失）；
- 运行、构建、类型检查、数据校验中暴露的问题；
- 脚本与文档不一致（文档写「可复现」，实际跑不通）；
- 性能与资源风险，且有明确触发条件。

**不要写这里：**

- 用户实际遇到的缺陷（优先放 [20-用户发现的Bug.md](./20-用户发现的Bug.md)；若同一问题，标「重复」并指向 `UB`）；
- 代码风格偏好、命名喜好、目录结构调整建议（放 `AR` 或直接讨论）；
- 没有证据的猜测（「这里可能会出问题」但说不出触发条件）；
- 安全问题细节（私下告知主控）。

**判定门槛：** 一条 `AB` 必须满足至少一项：有明确触发条件；有运行结果；有可指认的代码位置与逻辑矛盾。

## 2. 编号规则

- 从 `AB-001` 开始，三位数字，全局递增，**永不复用**。
- 示例条目固定使用 `AB-000`，不计入正式编号。
- 引用写全编号（如 `AB-003`）。
- 与 `UR`、`AR`、`UB` 编号互不共用。
- 同一根因的多个表现合并为一条，在「影响位置」里列全。

## 3. 状态与优先级

### 状态定义

| 状态 | 含义 |
|---|---|
| 待确认 | 已记录，等待主控判断是否为缺陷 |
| 已确认 | 主控确认是缺陷，等待排期 |
| 修复中 | 已建分支，正在修 |
| 待验证 | 修复已提交 PR，等待验证 |
| 已修复 | 验证通过并合并进 `main` |
| 无法复现 | 按记录的触发条件无法重复 |
| 不修复 | 确认存在但不修，必须写理由 |
| 重复 | 与已有条目重复，必须指向原编号 |

### 状态流转

```text
待确认 ──> 已确认 ──> 修复中 ──> 待验证 ──> 已修复
   │          │          │          │
   │          │          │          └──> 修复中（验证不通过）
   │          │          └──> 已确认（放弃当前修法）
   │          └──> 不修复（写理由）
   ├──> 无法复现（补充证据后可回到待确认）
   └──> 重复（终态，指向原编号）
```

规则：

1. **AI 不得自行把「待确认」改为「已确认」。** 确认权在主控。
2. 标「已确认」前必须有可重复的证据；仅凭代码阅读的，标注「静态推断」并给出置信度。
3. 「已修复」必须附 PR、验证命令与结果。
4. 「不修复」要写清风险接受理由。

### 优先级

| 优先级 | 判定标准 |
|---|---|
| P0 | 数据损坏或丢失、核心功能必然失败、安全风险 |
| P1 | 明确可触发且影响主要功能 |
| P2 | 边界条件下的错误，或体验明显受损 |
| P3 | 低频、影响小、可长期观察 |

AI 给出建议优先级，主控最终确定。

## 4. 字段说明

| 字段 | 必填 | 说明 |
|---|---|---|
| 编号 | 是 | `AB-xxx` |
| 标题 | 是 | 一句话描述缺陷，不超过 30 字 |
| 状态 | 是 | 初始为「待确认」 |
| 优先级 | 是 | `P0`–`P3`，建议值 |
| 发现方式 | 是 | 静态阅读 / 运行验证 / 类型检查 / 构建 / 数据校验 / 脚本审计 |
| 来源 | 是 | AI 名称、会话、日期 |
| 发现日期 | 是 | `YYYY-MM-DD` |
| 更新日期 | 是 | 最近修改日期 |
| 置信度 | 是 | 高 / 中 / 低；低置信度必须说明不确定点 |
| 是否复现 | 是 | 已复现 / 未复现（静态推断） |
| 触发条件 | 是 | 什么输入、状态或操作会触发 |
| 影响位置 | 是 | 文件与行号，必要时列多处 |
| 期望行为 | 是 | 按设计应该怎样 |
| 实际行为 | 是 | 代码实际会怎样，或运行结果 |
| 影响范围 | 否 | 受影响的功能与用户 |
| 证据 | 是 | 代码片段、命令输出、报错、校验结果 |
| 建议修复方向 | 否 | 思路与风险，不要求完整实现 |
| 关联条目 | 否 | 相关 `UR` / `AR` / `UB` / `Rxx` |
| 关联分支 / PR / 提交 | 否 | 修复时填写 |
| 负责人 | 否 | 修复者 |
| 根因 | 否 | 确认后填写 |
| 修复说明 | 否 | 改了什么，为什么 |
| 验证记录 | 否 | 命令、步骤、结果、验证人 |
| 备注 | 否 | 补充说明、变更记录 |

**触发条件**

对照区间覆盖 1852–1855，且列范围包含清朝中国 / 东亚。此时同一太平天国事件在四个年份各有一条记录，全部进入统计。

**影响位置**

- `public/events/1852.json:224-229`：`1852-008`「太平天国起义：攻占扬州并向上海扩张」，military
- `public/events/1853.json:238-243`：`1853-008`，标题与坐标同上
- `public/events/1854.json:318-323`：`1854-010`，标题与坐标同上
- `public/events/1855.json:86-91`：`1855-003`「太平天国起义：攻占扬州及叛军领土扩张」，military

- `src/components/CompareBoard.vue:92`：`count()` 按 `category` 逐条累加
- `src/lib/compare.ts:79-96`：`subjectEvents` 只按区域 / 政区范围过滤，不做事件去重

**期望行为**

**实际行为**

**影响范围**

对照界面的军事计数、按年分组与 `tiedYears`；同类逐年复述事件都会被放大。人物集合使用 `Set`，同名人物不会重复累加，但事件计数与分类统计会。具体影响幅度取决于查询区间长度。

**证据**

```text

1853.json:238  id 1853-008  同一标题与坐标                                  military
1854.json:318  id 1854-010  同一标题与坐标                                  military
1855.json:86   id 1855-003  "太平天国起义：攻占扬州及叛军领土扩张"          military
CompareBoard.vue:92  const count = (c) => events.filter((e) => e.category === c).length;
```

**建议修复方向**

在统计层按稳定事件键去重（例如标题归一化 + 坐标 + 类别，或引入事件系列 ID），再计算分类计数与按年分组。去重口径会改变现有对比数字，需主控确认后再实施。

## 7. 维护约定

1. **证据可核对。** 必须给文件与行号；行号会漂移，定位时以函数名和代码片段为准。
2. **区分「缺陷」与「建议」。** 能说出错误行为的是 `AB`；只是「可以更好」的是 `AR`。
3. **不重复登记。** 先检索 `UB` / `AB` / `REQUIREMENTS.md`；重复的指向原编号。
4. **不自行开工。** 状态未到「已确认 / 修复中」时，AI 不得修改代码。
5. **与进度跟踪同步。** 新增与状态变更在同一次提交中更新 [30-进度跟踪.md](./30-进度跟踪.md)。
6. **不删除条目。** 不修、无法复现的条目保留，写清原因。
7. **修复纪律：** 一次只修一条；不顺手重构；不改变无关行为；修完必须给出验证命令与结果。
