# AI 建议需求文档

> 编号前缀 `AR`　｜　本文件记录 AI 主动提出的改进建议。它是「建议」，不是已确认需求。
> 状态总览见 [30-进度跟踪.md](./30-进度跟踪.md)；用户需求见 [10-用户需求.md](./10-用户需求.md)。
> 维护：AI 可追加；双方均可确认、认领与交付；优先级分歧由用户拍板。
> 最后更新：2026-11-19（改为双向认领）

---

## 1. 用途与边界

本文件回答：**AI 在读代码、跑验证、对照用户反馈时，发现了什么值得改进的地方。**

**写这里：**

- 从代码现状推导出的体验改进、可维护性改进、可访问性改进；
- 与项目定位一致的效率提升（例如减少重复请求、缩短首屏时间）；
- 对已有需求的技术方案建议（作为 `AR` 条目，关联对应 `UR`）。

**不要写这里：**

- 用户明确提出的需求（放 [10-用户需求.md](./10-用户需求.md)）；
- 已确认的缺陷（放 [21-AI发现的Bug.md](./21-AI发现的Bug.md)）；
- 纯风格偏好（「我不喜欢这个命名」）——除非能说明实际影响；
- 已有 `Rxx` 或 `UR` 条目的重复内容，先检索再登记。

**判断标准：** 一条 `AR` 必须能回答「不做会怎样」。答不上来，就不要登记。

## 2. 编号规则

- 从 `AR-001` 开始，三位数字，全局递增，**永不复用**。
- 示例条目固定使用 `AR-000`，不计入正式编号。
- 引用写全编号（如 `AR-005`）。
- 与 `UR`、`UB`、`AB` 编号互不共用。
- 若主控决定并入项目主账本，在「主账本编号」回填 `Rxx`。

## 3. 状态与优先级

### 状态定义

| 状态 | 含义 |
|---|---|
| 待确认 | 建议已记录，收益与成本待评估 |
| 已确认 | 采纳，优先级已定，可以认领 |
| 已认领 | 已确定负责人，尚未开工 |
| 开发中 | 已建分支，负责人正在实现 |
| 待验收 | PR 已提交且自查通过，等待另一方验收 |
| 已完成 | 验收通过并合并进 `main` |
| 重新设计中 | 原型评审未通过，按反馈重做；不进入开发 |
| 待重新评审 | 已按反馈修改原型，等待再次评审 |
| 搁置 | 有价值但当前不做 |
| 已拒绝 | 不采纳，必须写明理由 |
| 已废弃 | 方案作废，编号保留；必须写明原因 |
| 重复 | 与已有条目重复，必须指向原编号 |

### 状态流转

```text
待确认 ──> 已确认 ──> 已认领 ──> 开发中 ──> 待验收 ──> 已完成
   │          │          │          │          │
   │          │          │          │          └──> 开发中（验收不通过）
   │          │          │          └──> 搁置 ──> 已确认
   │          │          └──> 已确认（放弃认领）
   │          └──> 搁置
   ├──> 重新设计中 ──> 待重新评审 ──> 已确认 / 已废弃
   ├──> 已废弃（终态，写原因）
   ├──> 已拒绝（终态，写理由）
   └──> 重复（终态，指向原编号）
```

规则：

1. **AI 不得自行把 `AR` 从「待确认」改为「已确认」。** 采纳由双方确认；AI 可代任一方执行，但必须得到该方明确指令。
2. 标「已完成」必须填写 PR / 提交与验收记录。
3. 「已拒绝」必须写清「为什么现在不做」，便于以后复盘。
4. 「已废弃」保留编号与原有内容，写明原因，不删除条目。
5. 原型评审结论写入对应条目的「原型评审反馈」，并同步 [30-进度跟踪.md](./30-进度跟踪.md)。
6. 「已认领」必须填负责人（人的姓名）、认领日期与认领方式（自领 / 转派 / 代领）；本文件、30、PR assignee 三处缺一不算认领。
7. 转派先取得现负责人同意，再写「负责人变更记录」；放弃认领回到「已确认」并释放负责人。
8. 同一编号同时只能有一位负责人；同时认领以认领日期较早者为准。

### 优先级

| 优先级 | 判定标准 |
|---|---|
| P0 | 不改会阻断演示、造成数据损坏或安全风险 |
| P1 | 明显影响核心体验或开发效率，且改动可控 |
| P2 | 有明确收益的改进，可以排期 |
| P3 | 锦上添花，可长期搁置 |

`AR` 的优先级是建议值，最终由双方协商确定，分歧由用户拍板。

#### AR-001 引入 GitHub Actions CI

- 编号：AR-001
- 状态：待确认
- 优先级：P2
- 来源：AI，2026-11-18 需求评审
- 提出日期：2026-11-18
- 更新日期：2026-11-18
- 负责人：未分配
- 主账本编号：无
- 关联条目：AR-002
- 备注：用户尚未表态

**建议依据**

`package.json` 已有 `typecheck`、`validate:data`、`build` 三个可直接执行的检查，但仓库没有 `.github/workflows/`，所有检查依赖人工在本地执行。非技术合作者容易漏跑。

**现状与问题**

PR 是否通过完全依赖提交者自律；主控需要逐次确认命令是否执行，协作成本高，也无法阻止类型或数据错误进入 `main`。

**建议方案**

- 方案 A：GitHub Actions 在 `pull_request` 与 `main` 的 push 上执行 `npm ci`、`npm run typecheck`、`npm run validate:data`、`npm run build`，使用 npm 缓存。
- 方案 B：只跑 `typecheck` 与 `build`，缩短反馈时间，数据校验留给本地。

**预期收益**

自动阻断类型、数据与构建回归；给合作者明确的通过/失败信号；减少主控的重复确认。

**实现成本与风险**

- 成本：一个 workflow 文件；需要处理 Cesium 静态资源拷贝带来的构建时间。
- 风险：Actions 额度与构建时长；`verify:smoke` 依赖浏览器，暂不纳入。
- 回退：删除 workflow 文件即可，不影响本地命令。

**验收标准**

- [ ] PR 上出现 CI 检查项，能区分通过、失败与进行中
- [ ] 检查实际执行 `typecheck`、`validate:data`、`build`
- [ ] 失败时日志能直接定位到具体命令与报错
- [ ] 不依赖仓库 secrets 即可运行
- [ ] 若启用分支保护，失败检查可阻止合并

**建议依据**

**现状与问题**

#### AR-003 年份文件按十年或五十年合并分片

- 状态：待确认
- 优先级：P2
- 来源：AI，2026-11-18 需求评审

- 负责人：未分配
- 主账本编号：无
- 关联条目：无

**建议依据**

`public/events/` 目前按年份存放 JSON，约有 260 个年份文件；时间轴跨年拖动会触发多次按年请求。

**现状与问题**

请求数量多，弱网或快速拖动时首屏与切换等待明显；HTTP/2 虽可复用连接，但每文件仍有解析与调度开销。

**建议方案**

- 方案 A：按十年合并，例如 `1850s.json`，保留年份字段，客户端按年过滤。
- 方案 B：按五十年合并，进一步减少请求，但单文件更大、首次加载更重。

**预期收益**

减少请求数与切换等待，改善时间轴拖动体验；为搜索索引的构建提供更粗的读取单元。

**实现成本与风险**

- 成本：迁移脚本、加载逻辑、校验脚本与缓存策略都要调整。
- 风险：单文件体积变大；按年加载粒度变粗；旧链接或旧缓存需要兼容。
- 回退：保留原始年份文件生成能力，切回按年加载。

**验收标准**

#### AR-004 构建门禁 validate:trust

- 编号：AR-004
- 状态：待确认
- 优先级：P2
- 来源：AI，2026-11-18 需求评审
- 提出日期：2026-11-18
- 更新日期：2026-11-18
- 负责人：未分配
- 主账本编号：无
- 关联条目：AR-001、UR-002
- 备注：建议等可信度台账建好后再上

**建议依据**

当前构建只校验数据结构与字段，无法判断内容是否有来源、是否经过审查。UR-002 已确认暂停数据扩张、优先来源与 AI 标识，需要配套的强制检查。

**现状与问题**

无来源或未审查的内容可以进入构建；是否可信依赖人工记忆，无法在合并前拦截。

**建议方案**

- 先建立可信度台账（来源、AI 标识、审查状态、审查人）。
- 提供 `validate:trust` 脚本，检查每个内容条目是否有台账记录。
- 初期只 dry-run 输出覆盖率，覆盖率稳定后再接入构建门禁；缺失台账时构建失败。

**预期收益**

把「内容可信」从口头约定变成可执行门禁；为后续审查与展示提供统一数据。

**实现成本与风险**

- 成本：全量补台账工作量大；需要定义 schema 与例外清单。
- 风险：过早启用会阻断现有构建；台账维护可能滞后于内容修改。
- 回退：门禁做成可开关，必要时降级为警告。

**验收标准**

- [ ] 台账 schema 明确字段与唯一键
- [ ] dry-run 能输出覆盖率与缺失清单
- [ ] 门禁开启后，无台账条目会导致构建失败并指出条目
- [ ] 提供例外清单与降级为警告的方式
- [ ] 先在 CI 观察一段时间，再决定是否强制

#### AR-005 不引入外部历史地图集

- 编号：AR-005
- 状态：待确认
- 优先级：P3
- 来源：AI，2026-11-18 需求评审
- 提出日期：2026-11-18
- 更新日期：2026-11-18
- 负责人：未分配
- 主账本编号：无
- 关联条目：UR-008
- 备注：用户尚未表态

**建议依据**

引入外部历史地图集或学术 GIS 会带来许可、坐标体系、数据口径与工作量问题；项目定位是个人开发的开源项目，当前数据已能支撑演示。

**现状与问题**

现有数据精度有限，但界面没有明确说明精度上限；用户可能把示意边界当作精确边界。

**建议方案**

- 不引入外部历史地图集或学术 GIS。
- 将现有数据源作为精度上限，在关于页与地图图例标注「历史势力范围示意」。
- 在文档中说明数据来源、精度限制与不保证史实准确。

**预期收益**

控制范围与合规风险；管理用户对精度的预期；避免大规模数据迁移。

**实现成本与风险**

## 7. 维护约定

1. **先检索再登记。** 先看 `REQUIREMENTS.md`、`UR`、已有 `AR`，避免重复。
2. **一条建议一件事。** 不把「重构 + 新功能 + 改文档」打包成一条。
3. **证据优先。** 涉及代码的写文件与行号；涉及行为的写复现条件。
4. **不夸大。** 不确定收益就写「不确定」，不要编造数据。
5. **与进度跟踪同步。** 新增与状态变更在同一次提交中更新 [30-进度跟踪.md](./30-进度跟踪.md)。
6. **不删除条目。** 被拒绝的条目保留，写清理由。
7. **实现前必须等「已认领」。** 条目未认领、或负责人不是本方时，AI 只能补充分析，不能动代码。
8. **不与其他文档抢编号。** `AR` 只用于 AI 建议，用户需求永远用 `UR`。
9. **认领与转派单独提交。** 提交信息以编号为范围，例如 `docs(AR-007): claim by 张三`。
