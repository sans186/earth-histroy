# AI 建议需求文档

> 编号前缀 `AR`　｜　本文件记录 AI 主动提出的改进建议。它是「建议」，不是已确认需求。
> 状态总览见 [30-进度跟踪.md](./30-进度跟踪.md)；用户需求见 [10-用户需求.md](./10-用户需求.md)。
> 维护：AI 可追加；采纳、拒绝、优先级由主控决定。
> 最后更新：2026-11-18（初稿）

---

## 1. 用途与边界

本文件回答：**AI 在读代码、跑验证、对照用户反馈时，发现了什么值得改进的地方。**

**写这里：**

- 从代码现状推导出的体验改进、可维护性改进、可访问性改进；
- 与项目定位一致的效率提升（例如减少重复请求、缩短首屏时间）；
- 对已有需求的技术方案建议（作为 `AR` 条目，关联对应 `UR`）。

**不要写这里：**

- 用户明确提出的需求（放 [10-用户需求.md](./10-用户需求.md)）；
- 已确认的缺陷（放 [21-AI发现的Bug.md](./21-AI发现的Bug.md)）；
- 纯风格偏好（「我不喜欢这个命名」）——除非能说明实际影响；
- 已有 `Rxx` 或 `UR` 条目的重复内容，先检索再登记。

**判断标准：** 一条 `AR` 必须能回答「不做会怎样」。答不上来，就不要登记。

---

## 2. 编号规则

- 从 `AR-001` 开始，三位数字，全局递增，**永不复用**。
- 示例条目固定使用 `AR-000`，不计入正式编号。
- 引用写全编号（如 `AR-005`）。
- 与 `UR`、`UB`、`AB` 编号互不共用。
- 若主控决定并入项目主账本，在「主账本编号」回填 `Rxx`。

## 3. 状态与优先级

### 状态定义

| 状态 | 含义 |
|---|---|
| 待确认 | 建议已记录，收益与成本待评估 |
| 已确认 | 主控采纳，优先级已定，可以排期 |
| 开发中 | 已建分支，正在实现 |
| 待验收 | PR 已提交且自查通过，等待主控验收 |
| 已完成 | 验收通过并合并进 `main` |
| 搁置 | 有价值但当前不做 |
| 已拒绝 | 不采纳，必须写明理由 |
| 重复 | 与已有条目重复，必须指向原编号 |

### 状态流转

```text
待确认 ──> 已确认 ──> 开发中 ──> 待验收 ──> 已完成
   │          │          │          │
   │          │          │          └──> 开发中（验收不通过）
   │          │          └──> 搁置 ──> 已确认
   │          └──> 搁置
   ├──> 已拒绝（终态，写理由）
   └──> 重复（终态，指向原编号）
```

规则：

1. **AI 不得自行把 `AR` 从「待确认」改为「已确认」。** 采纳权在主控。
2. 标「已完成」必须填写 PR / 提交与验收记录。
3. 「已拒绝」必须写清「为什么现在不做」，便于以后复盘。

### 优先级

| 优先级 | 判定标准 |
|---|---|
| P0 | 不改会阻断演示、造成数据损坏或安全风险 |
| P1 | 明显影响核心体验或开发效率，且改动可控 |
| P2 | 有明确收益的改进，可以排期 |
| P3 | 锦上添花，可长期搁置 |

`AR` 的优先级是建议值，最终由主控确定。

## 4. 字段说明

| 字段 | 必填 | 说明 |
|---|---|---|
| 编号 | 是 | `AR-xxx` |
| 标题 | 是 | 一句话说清建议，不超过 30 字 |
| 状态 | 是 | 初始为「待确认」 |
| 优先级 | 是 | `P0`–`P3`，建议值 |
| 来源 | 是 | 哪个 AI / 会话 / 日期，以及观察渠道 |
| 提出日期 | 是 | `YYYY-MM-DD` |
| 更新日期 | 是 | 最近修改日期 |
| 建议依据 | 是 | 代码位置、运行现象、用户反馈、数据统计等 |
| 现状与问题 | 是 | 现在是什么样，为什么不够好 |
| 建议方案 | 是 | 建议怎么做，可以是多个方案 |
| 预期收益 | 是 | 改善什么，尽量可度量 |
| 实现成本 | 是 | 大致改动范围与风险点，不写精确工时 |
| 风险与副作用 | 是 | 可能影响的功能、性能、数据 |
| 验收标准 | 是 | 可观察的完成条件 |
| 不做的理由 | 否 | 选择不做时必须写 |
| 关联条目 | 否 | 相关 `UR` / `UB` / `AB` / `Rxx` |
| 主账本编号 | 否 | 并入主账本时填 `Rxx` |
| 关联分支 / PR / 提交 | 否 | 开发后填写 |
| 负责人 | 否 | 实现者 |
| 主控决策 | 否 | 采纳 / 拒绝 / 搁置，以及理由与日期 |
| 备注 | 否 | 补充说明、变更记录 |

### 填写示例

> `AR-000` 为示例编号，不计入统计；示例内容为虚构，仅示范字段写法，请勿实现。

#### AR-000 时间轴输入框支持中文年份写法

- 编号：AR-000（示例）
- 状态：待确认
- 优先级：P3
- 来源：AI（示例会话），2026-11-18，阅读 `src/components/TimeScale.vue` 后提出
- 提出日期：2026-11-18
- 更新日期：2026-11-18
- 负责人：未分配
- 主账本编号：无
- 关联条目：无
- 备注：无

**建议依据**

时间轴输入框目前以数字年份为主（示例假设）。用户可能输入「公元前 221 年」「公元 1912 年」这类中文写法，需要先自己换算成负数或纯数字。

**现状与问题**

中文写法无法直接跳转，输入后可能被判为无效并保持原年份，用户不知道是格式问题还是功能坏了。

**建议方案**

- 方案 A：解析「公元前 / 前 / BC」前缀与「公元 / AD」后缀，统一转换成内部年份；无法解析时保持原年份并给出简短提示。
- 方案 B：不改解析，只在输入框旁补一行格式示例。

**预期收益**

降低输入门槛，减少「输了没反应」的困惑。收益不可精确度量。

**实现成本与风险**

- 成本：只改 `TimeScale.vue` 与 `i18n.ts`，规模小。
- 风险：「前 221」「-221」等边界写法可能误解析，需要覆盖测试。
- 回退：revert 对应 PR 即可，无数据变更。

**验收标准**

- [ ] 输入「公元前 221 年」跳到 -221
- [ ] 输入「公元 1912 年」跳到 1912
- [ ] 输入无法解析的内容时保持原年份，并显示提示
- [ ] 原有纯数字与负数输入行为不变
- [ ] 中英文提示文案齐全

**关联分支 / PR / 提交**

- 分支：未开始
- PR：无
- 提交：无

**主控决策**

- 结论：待定
- 理由：
- 日期：

## 7. 维护约定

1. **先检索再登记。** 先看 `REQUIREMENTS.md`、`UR`、已有 `AR`，避免重复。
2. **一条建议一件事。** 不把「重构 + 新功能 + 改文档」打包成一条。
3. **证据优先。** 涉及代码的写文件与行号；涉及行为的写复现条件。
4. **不夸大。** 不确定收益就写「不确定」，不要编造数据。
5. **与进度跟踪同步。** 新增与状态变更在同一次提交中更新 [30-进度跟踪.md](./30-进度跟踪.md)。
6. **不删除条目。** 被拒绝的条目保留，写清理由。
7. **实现前必须等「已确认」。** 状态未到「已确认」时，AI 只能补充分析，不能动代码。
8. **不与其他文档抢编号。** `AR` 只用于 AI 建议，用户需求永远用 `UR`。
