## 1. 项目定位与设计主旨

### 1.1 一句话定位

**横向历史对比工具**：在同一个时间切片上，横向对比全球各文明的处境；再沿时间轴纵向追溯每一文明的演变。

这不是一个"历史事件地图"，也不是"时间轴百科"。它的价值锚点是**对比（comparison）**，而非陈列（display）。原始可行性报告里反复出现的 ChronoGlobe / ChronoZoom / HiGIS，都验证了同一件事：3D 地球 + 非线性时间轴是这类产品的标准形态，但**真正稀缺的是"同一时刻的横向可比"**。

### 1.2 五条设计主旨

| # | 主旨 | 对设计的约束 |
|---|------|-------------|
| 1 | **时间优先于地点** | 时间是第一维度，地球是时间的载体。任何界面元素都要能被"年份"驱动 |
| 2 | **对比优先于陈列** | 必须有"同一时刻多区域并列"的能力，而不是只能一次看一个点 |
| 3 | **证据可追溯** | 每个事件都要可回到史料来源、可信度、史学争议。现数据已含 `sources` / `certainty` / `historiographic_note` 字段，但界面上完全没有暴露 |
| 4 | **视图分离、按需获取** | 3D / 2D / 时间轴 / 面板各自独立渲染，按时段 + 空间范围向后端要数据，绝不一次性灌全量 |
| 5 | **非线性时间** | 公元前压缩、近现代拉伸。这是体验核心，必须保留并有视觉表达 |

### 1.3 目标用户与核心场景

| 用户 | 场景 | 关键诉求 |
|------|------|---------|
| 历史爱好者 | 按年份漫游，看这一年世界正在发生什么 | 沉浸、流畅、信息密度合适 |
| 学生 / 教师 | 讲"同一时期的中国与罗马"，做课堂演示 | 横向并列、可截图、可引用 |
| 内容创作者 | 取材写稿，需要可靠出处 | 溯源、引用格式、导出 |
| 研究者 | 检索特定时空范围的事件与政区 | 精确筛选、数据可导出 |

### 1.4 与现有实现的关系

| 资产 | 处置 |
|------|------|
| `public/` 数据集（约 250MB） | **全部保留**，但需几何简化、量化、入库 |
| `scripts/` 数据流水线 | 保留逻辑，重写为可复现的 TS 脚本 |
| `src/` 前端源码 | **重写**（微内核 + 插件 → Vue 3 + Service 层） |
| 3 套旧主题 | **废弃删除**（已确认，见 2.5） |
| 部署链路 | 保留 nginx，增加后端服务 |

### 2.2 设计系统骨架

无论最终选哪套方向，下列令牌体系是共用的。方向确认后填入具体色值。

**色彩令牌**

```
--bg / --surface / --surface-2      背景层级（3 级）
--line / --line-2                   分隔线（1px 发丝线为主）
--text / --text-2 / --text-3        文字层级（正文 / 次要 / 标签）
--accent                            唯一强调色（当前状态、选中、主操作）
--cat-political / military / economic / cultural / technological / exploration
                                    六类事件色（需在所选底图上有足够对比度）
--ok / --warn / --danger            状态色
```

**字号阶梯**（1.2 倍比，桌面端）

| 令牌 | 字号 | 用途 |
|------|------|------|
| `--fs-display` | 40-44px | 年份大字、页面主标题 |
| `--fs-h1` | 26px | 区块标题 |
| `--fs-h2` | 19px | 卡片标题 |
| `--fs-h3` | 15px | 列表条目标题 |
| `--fs-body` | 13px | 正文 |
| `--fs-sm` | 12px | 次要说明 |
| `--fs-label` | 10px + `letter-spacing: .18em` + uppercase | 微标签 |

**间距阶梯**：4 / 8 / 12 / 16 / 22 / 30 / 44（px），全部为 2 的倍数以适配 2x 屏。
**圆角**：随方向而定，A/B 取 0-2px，C 取 4-6px，D 取 0-4px。禁止混用。
**阴影**：最多两级（浮层 / 弹窗）。深色方向以线框代替阴影。

**必要状态**（当前项目几乎全部缺失，必须补齐）

| 状态 | 要求 |
|------|------|
| Loading | 分层骨架屏：地球骨架 + 面板骨架 + 时间轴骨架，而非全屏遮罩 |
| Empty | "该年份无收录事件" + 引导到相邻年份，而非空白 |
| Error | 具体错误 + 重试 + 降级方案（如政区加载失败时保留事件层） |
| Partial | 部分世纪文件加载失败时，明确标注哪部分缺失（当前是静默吞掉） |
| Focus | 全键盘可达，焦点环 2px accent，`Tab` 顺序符合视觉顺序 |
| Hover | 政区高亮用**描边加粗 + 填充提亮**，不允许"取消填充"（现 bug） |

**可访问性目标**：正文对比度 ≥ 4.5:1，大字 ≥ 3:1；不使用纯色作唯一区分手段（事件分类同时用形状/文字）；`prefers-reduced-motion` 时关闭自动播放与飞行动画。

### 2.3 页面结构与核心交互流

**主界面（App Shell）**：顶部导航 / 左侧事件编年 / 中央地球 / 右侧图层控制 / 底部时间轴 / 事件详情卡（浮层）。

**交互流 1 · 时间漫游**
```
拖动时间轴 → 年份变更（debounce 100ms）
  → 并行：加载事件窗口（±20 年） / 加载政区（当前世纪 ±1，空间裁剪）
  → 地球重绘标记 + 政区着色
  → 左侧列表刷新，详情卡若已打开则跟随更新
```

**交互流 2 · 横向对比（核心，当前完全缺失）**
```
选择对比模式 → 时间轴拆分为 N 条并列轨道（或地球分屏）
  → 用户在每条轨道上选择区域/文明
  → 同一时间切片下，各区域的事件、政区、人口并列展示
  → 可锁定时间，仅横向切换区域
```

**交互流 3 · 溯源**
```
点击事件 → 详情卡 → 点击"来源与可信度"
  → 展开史料列表（名称/类型/是否同时代）、可信度评级、史学争议说明
  → 提供引用格式复制（GB/T 7714 / BibTeX）
```

### 2.7 质量门

| 门禁 | 命令 | 作用 |
|------|------|------|
| 类型检查 | `npm run typecheck`（vue-tsc） | Vite 不做类型校验，HTTP 200 无法暴露类型错误 |
| 数据校验 | `npm run validate:data`，并挂到 `prebuild` | 数据不合格则构建失败 |

## 3. 技术栈选型（作用 · 优点 · 缺点）

> 每项给出：承担什么、好在哪、代价是什么、本项目结论。

### 3.1 前端

#### Vue 3（Composition API + `<script setup>`）

- **作用**：UI 层的声明式渲染与组件化。取代当前手写 DOM / `innerHTML`。
- **优点**：响应式心智模型清晰；单文件组件便于按面板拆分巨型插件；模板插值自动转义，天然消除现存的 XSS 风险；`onUnmounted` 自动清理副作用，直接解决当前"监听器只增不减"的泄漏。
- **缺点**：Vue 的响应式基于 Proxy，**绝不能包裹 Cesium / MapLibre 对象**，否则高频属性访问会性能雪崩甚至异常；需要团队建立"UI 用 Vue、引擎用命令式"的纪律。
- **结论**：**采用**。4 个 800-1300 行的巨型插件是当前最大的维护负担，Vue 组件化是对症的。

#### TypeScript

- **作用**：静态类型约束。当前项目事件 / 政区 / 人物 / 战争四套数据结构各不相同且无校验。
- **优点**：把数据契约写进代码；重构时编译器帮你找齐所有引用点；对 `polity` / `war` 这类字段极多的结构收益最大。
- **缺点**：初期有学习与书写成本；Cesium 的类型定义不总是准确，偶需 `as` 断言；单文件会变长。
- **结论**：**采用**。这是治理数据混乱的前置条件，不建议跳过。

#### Vite

- **作用**：开发服务器 + 生产构建。
- **优点**：当前已在用，冷启动快、ESM 原生；Cesium 静态资源拷贝与 gzip 预压缩方案已跑通，迁移成本几乎为零。
- **缺点**：对 Cesium 这类含 Worker 的重型库，配置略繁琐；生产构建不做自动按路由分割（本项目单页，影响小）。
- **结论**：**保留**（升级到最新版）。

#### Pinia

- **作用**：全局状态管理。取代自研 `state.js` + `event-bus.js`。
- **优点**：官方方案、DevTools 时间旅行调试、类型友好（TS 推断最佳）；`persistedstate` 插件可替代自写 localStorage 逻辑。当前 Store 与 EventBus 职责重叠、隐藏键（`_map2d` / `_trajectoryActive`）无契约，Pinia 能把它们变成有类型的 state。
- **缺点**：需要区分"UI 状态进 Pinia / 引擎对象不进 Pinia"，边界管不好会把 Cesium 对象漏进去。
- **结论**：**采用**，同时废弃 EventBus（其"瞬时事件"职责由 Pinia action + 组件事件承担）。

#### Naive UI

- **作用**：提供表单控件（滑块、开关、下拉、数字输入），主要服务于开发者设置面板的 35+ 参数。
- **优点**：TypeScript 优先、无全局样式污染、主题变量可覆盖，能和自研设计令牌共存；按需引入体积可控。
- **缺点**：默认视觉是通用后台风格，若大量使用会稀释样稿的设计感；必须做主题覆盖才不会"一眼看就是组件库默认皮"。
- **结论**：**有条件采用**。只用于复杂表单控件（DevSettings），侧栏、卡片、时间轴等视觉主体仍自研。若确认走 A/B 方向（强版式风格），可改为引入无样式的 headless 方案（Radix Vue），进一步降低污染。

#### CesiumJS

- **作用**：3D 地球引擎。实体、影像图层、拾取、相机。
- **优点**：开源、无商业授权费、时空数据支持成熟；当前项目已深度使用（Entity / ImageryProvider / GeoJsonDataSource / drillPick），换引擎等于重写。
- **缺点**：**必须依赖 Ionic Token**（`config.js` 里那个硬编码 token，须外置并设置允许域名）；单 Entity 数量上千就明显掉帧，政区必须迁移到 `Primitive` 批处理或 MVT 图层；官方 API 有私有字段（当前代码用了 `scene._targetFrameRate` 等，升级必炸）；包体积大。
- **结论**：**保留**，但渲染层必须从 Entity 迁移到 Primitive / 矢量瓦片。

#### MapLibre GL JS

- **作用**：2D 平面地图。
- **优点**：Mapbox GL 的开源分叉，无授权费；WebGL 渲染、性能好；GeoJSON 与 MVT 都原生支持。
- **缺点**：与 Cesium 需要各自维护一套渲染逻辑（当前 `map2d-renderer.js` 与 `layers-plugin.js` 大量重复代码）；两套坐标系与相机状态同步是调试难点。
- **结论**：**保留**，但两套渲染器要抽出共享的 Service 与数据适配层，消除重复。

#### @turf/turf

- **作用**：浏览器端空间运算（面积、相交、裁剪、抽稀）。
- **优点**：纯 JS，API 丰富，无需服务端即可做轻量空间计算。
- **缺点**：**性能一般**，大数据量下在主线程跑会直接卡死（当前政区处理就是主线程瓶颈之一）；精确度不如 PostGIS。
- **结论**：**保留但降级使用**。仅用于交互时的轻量计算；批量几何处理移到构建期（`scripts/data/simplify-polities.mjs`）或服务端（PostGIS）。

#### Vitest + Playwright

- **作用**：单元测试 + 端到端测试。
- **优点**：Vitest 与 Vite 同源、配置零成本；Playwright 可覆盖 Cesium 的画布交互（拾取、拖拽）。
- **缺点**：Cesium 的 WebGL 渲染结果难以做像素级断言，测试稳定度需要调试；初期见效慢。
- **结论**：**采用**。优先覆盖纯函数（`sliderToYear` / `yearToSlider` / 坐标解析 / 颜色哈希）与关键交互流。

### 3.2 构建期与数据处理

#### 几何简化：自研脚本（原计划 mapshaper）

- **背景**：mapshaper 无法安装 —— 其依赖 `@ngageoint/geopackage@^4.2.10` 在当前 npm registry 解析失败（ETARGET）。
- **替代**：自研 `scripts/data/simplify-polities.mjs`，内含 Douglas-Peucker（按环尺寸自适应容差）、坐标量化、属性裁剪与预压缩产出。
- **优点**：零新增依赖；容差、精度、保留字段完全可控；附带结构校验与 `index.json` 重建。
- **缺点**：不具备 mapshaper 的拓扑修复能力；自研代码需自行维护验证。
- **结论**：**采用，已实施完成**。实测把 183.6 MB 压到 52.4 MB（gzip 后 13.8 MB），见 6.6 节。

#### TopoJSON + 坐标量化

- **作用**：把 GeoJSON 转为共享弧段 + 定点量化的格式。
- **优点**：相邻多边形共享边界，体积可再降 60-80%；量化后渲染更快；天然消除相邻边界缝隙。
- **缺点**：需要引入 `topojson-client` 在运行时解码，多一层转换；调试时不可读。
- **结论**：**采用**。适合 `polities` 这种高度共享边界的政区数据。

#### tippecanoe

- **作用**：把 GeoJSON 预切成矢量瓦片（MVT / pbf）。
- **优点**：按缩放级别分层输出，前端只加载视口内瓦片，彻底解决"一次性 38MB"的问题；生态成熟（Mapbox 出品）。
- **缺点**：需要本地编译或装二进制；切片是一次性离线任务，数据更新要重切；调参（简化率、最小缩放）需要经验。
- **结论**：**采用**。这是横向对比与快速漫游的性能前提。

#### zod

- **作用**：运行时数据校验（Schema）。
- **优点**：TS 类型与运行时校验同一份定义；能在构建期就拦住 `index.json` 引号损坏、`-1.json` 年份不一致这类问题。
- **缺点**：增加依赖；校验大 JSON 有性能开销（构建期无所谓）。
- **结论**：**采用**。四套数据结构必须上 Schema + `schemaVersion`。

#### tsx

- **作用**：直接运行 TypeScript 脚本，替代当前 `.cjs`。
- **优点**：脚本与业务共享类型定义；免编译；支持 ESM。
- **缺点**：生产环境不用它，只是开发期工具；偶尔有 ESM/CJS 混用坑。
- **结论**：**采用**。

### 3.3 后端（Java 栈）

#### JDK 17 或 21

- **作用**：运行 Spring Boot 3。
- **说明**：Spring Boot 3 的最低要求是 **JDK 17**。注意你现有项目用的是 JDK 11，本项目的后端**必须升到 17+**。
- **优点**：ZGC / 虚拟线程（21）对 IO 密集型查询服务友好；新语法（record / sealed / switch 表达式）显著减少样板代码。
- **缺点**：与旧项目环境并存时需管理多 JDK；部分旧库可能不兼容 17。
- **结论**：**采用 JDK 21（LTS）**，若企业环境受限则 17。

#### Spring Boot 3.x

- **作用**：后端 Web 服务框架、依赖注入、配置、自动装配。
- **优点**：生态最完整；你已熟悉（前一个项目即是此栈），学习成本几乎为零；与 MyBatis-Plus / Sa-Token / Redis 等集成成熟；`springdoc-openapi` 可自动生成 API 文档。
- **缺点**：相比 Fastify/FastAPI，**启动更慢、内存占用更高、开发热重载体验更差**；对 GeoJSON 这类"半结构化大对象"的处理不如 Node/Python 顺手，需要额外引入 Jackson 的 GIS 模块；构建产物大。
- **结论**：**采用**（已确认）。理由是你的既有技术栈与运维习惯，长期维护成本低于切换语言。

#### Spring Validation + 全局异常处理

- **作用**：入参校验与统一错误响应。
- **优点**：声明式校验，减少手写 if；统一错误码便于前端处理。
- **缺点**：复杂业务规则仍需手写。
- **结论**：**采用**。

#### MyBatis-Plus

- **作用**：数据访问层（CRUD + 条件构造器 + 分页）。
- **优点**：你已熟悉；SQL 可控（对空间查询这类需要精确控制 SQL 的场景很重要）；代码生成器可省掉大量样板；与 PostGIS 函数（`ST_*`）可以无缝混写。
- **缺点**：比 JPA 更"手写 SQL"，跨数据库能力弱（但本项目锁定 PostgreSQL，无影响）；过度依赖其 Wrapper 会让复杂查询可读性变差。
- **结论**：**采用**。

#### PostgreSQL 16 + PostGIS 3.4

- **作用**：主数据库 + 空间扩展。
- **优点**：Cliopatria 是时序多边形数据，PostGIS 提供 `GiST` 空间索引、`ST_Intersects` 视口裁剪、`ST_Simplify` 动态简化、`ST_AsMVT` 直接产出矢量瓦片；这是**唯一能优雅支撑本项目空间查询的方案**。
- **缺点**：运维比 MySQL 稍复杂；PostGIS 函数学习曲线；你此前用的是 MySQL，需要一次迁移。
- **结论**：**必须采用**。MySQL 无空间索引能力，本项目不具备可行性（这也是原始报告里"后续迁移 PostgreSQL+PostGIS"的建议，直接前置执行）。

#### Redis

- **作用**：缓存瓦片、热点查询、会话。
- **优点**：把 MVT 与常用查询缓存住，DB 压力骤降；支持空间数据类型（GEO），可做邻近检索。
- **缺点**：多一个中间件要运维；缓存一致性要设计失效策略。
- **结论**：**采用**，但排在 Phase 4 后期，前期先用 Spring Cache + Caffeine 本地缓存即可。

#### Martin（PostGIS → MVT 瓦片服务）

- **作用**：直接从 PostGIS 表发布矢量瓦片，替代手写切片接口。
- **优点**：Rust 编写，性能极高；配置极简（一个连接串 + 表名）；支持 `ST_AsMVT` 聚合；避免了"自己写瓦片接口"这个典型坑。
- **缺点**：多一个独立进程；配置灵活性不如代码可控（复杂过滤需要 SQL 视图配合）。
- **结论**：**采用**。备选 `pg_tileserv`（Go 编写，功能相近）。

#### Flyway（或 Liquibase）

- **作用**：数据库版本迁移。
- **优点**：SQL 脚本化，环境一致；数据修复（如修 `index.json` 对应的表数据）可追溯。
- **缺点**：迁移脚本写错难以回滚（需手写 undo）。
- **结论**：**采用 Flyway**（更贴近手写 SQL 的习惯）。

#### springdoc-openapi

- **作用**：根据注解生成 Swagger UI。
- **优点**：前后端联调时接口即文档；减少口头/文档同步成本。
- **缺点**：注解有侵入性；复杂 DTO 生成的文档可读性一般。
- **结论**：**采用**。

#### Sa-Token

- **作用**：认证鉴权。
- **优点**：你已熟悉；轻量、API 简洁、易与 Spring Boot 3 集成。
- **缺点**：功能不如 Spring Security 完备（对 OAuth2 / 复杂授权场景支持弱）。
- **结论**：**Phase 5 引入**。仅当落地"用户提交 / 收藏 / 笔记"等需要身份的功能时才需要，前期无用户体系，不必过早引入。

### 3.4 基础设施与运维

| 组件 | 作用 | 优点 | 缺点 | 结论 |
|------|------|------|------|------|
| Nginx | 静态资源 + 反向代理 + gzip_static | 现已在用，配置已跑通 | 需要额外配后端反代与超时 | 采用 |
| Docker + Compose | 后端 + PG + Redis + Martin 编排 | 一键起环境，与生产一致 | 增加一层学习与运维 | 采用 |
| 阿里云 OSS + CDN | 大体积瓦片与数据的对象存储与分发 | 现有服务器在阿里云，内网打通延迟低 | 有流量成本 | 采用 |
| Sentry | 前端错误采集 | 现项目错误全靠 `console`，线上问题不可见 | 需接入配置 | 建议采用 |
| GitHub Actions | CI：lint + tsc + test + build | 免费额度足够 | 需要写 workflow | 建议采用 |

### 3.5 明确不采用

| 不采用 | 原因 |
|--------|------|
| Nuxt / SSR | Cesium 强依赖 `window`，SSR 零收益，纯增复杂度 |
| 微前端 / qiankun | 单人项目，过度设计 |
| Element Plus / Ant Design Vue 全量引入 | 与样稿设计语言冲突，且体积大 |
| MySQL 存多边形 | 无空间索引，项目不可行 |
| 250MB GeoJSON 原样入库 / 原样部署 | 必须先经几何简化（已完成）+ tippecanoe 切片（待办） |
| 全盘用 Vue 包裹 Cesium | Proxy 化引擎对象会导致性能崩溃 |
| GeoServer | 相比 Martin 过重，且对本项目的动态过滤需求支持笨拙 |
| Electron / 桌面端 | 无此需求 |
| 图数据库 Neo4j（当前） | 人物 / 事件关系用 PostgreSQL 递归查询 + 邻接表已足够，Phase 5 若关系规模爆炸再评估 |

### 4.2 前端分层规则

| 层 | 允许 | 禁止 |
|----|------|------|
| 组件层 | 读 Pinia、调用 Service、渲染 | 直接操作 Cesium 实例、直接 `fetch` |
| Service 层 | 持有 Cesium/MapLibre 实例、请求 API、操作引擎 | 直接操作 DOM、被 `reactive` 包裹 |
| Store | 存 UI 状态与配置 | 存 Cesium 对象、MapLibre 实例 |

关键约束：Service 层导出的引擎对象必须用 `markRaw` 或不进入响应式体系。

### 4.3 后端分层

```
controller/   REST 入口，参数校验（@Valid），无业务逻辑
service/      业务编排、事务边界
mapper/       MyBatis-Plus + 自定义 SQL（PostGIS 函数写在这里）
domain/       实体（对应表）
dto/          出入参对象（与实体分离，避免表结构外泄）
config/       CORS、Jackson、缓存、OpenAPI、异常处理
```

### 4.4 数据模型草案

```sql
-- 历史事件
CREATE TABLE event (
  id            BIGSERIAL PRIMARY KEY,
  year          INT          NOT NULL,     -- 负值为公元前
  year_label    VARCHAR(64),
  title         VARCHAR(255) NOT NULL,
  region        VARCHAR(128),
  category      VARCHAR(32)  NOT NULL,     -- political/military/...
  geom          GEOMETRY(Point, 4326),
  description   TEXT,
  certainty     VARCHAR(32),
  certainty_note TEXT,
  source_locale VARCHAR(8)   NOT NULL DEFAULT 'zh',
  schema_version SMALLINT    NOT NULL DEFAULT 1
);
CREATE INDEX idx_event_year_cat ON event(year, category);
CREATE INDEX idx_event_geom     ON event USING GIST(geom);
CREATE INDEX idx_event_search   ON event USING GIN(to_tsvector('simple', title || ' ' || description));

-- 事件来源（一对多）
CREATE TABLE event_source (
  id BIGSERIAL PRIMARY KEY, event_id BIGINT REFERENCES event(id),
  name VARCHAR(255), type VARCHAR(64), contemporary BOOLEAN, url TEXT
);

-- 历史政区（Cliopatria）
CREATE TABLE polity (
  id BIGSERIAL PRIMARY KEY,
  name VARCHAR(255) NOT NULL,
  name_zh VARCHAR(255),
  wikipedia VARCHAR(255),
  from_year INT, to_year INT,
  area DOUBLE PRECISION,
  geom GEOMETRY(MultiPolygon, 4326)
);
CREATE INDEX idx_polity_years ON polity(from_year, to_year);
CREATE INDEX idx_polity_geom  ON polity USING GIST(geom);

-- 政区资产（国旗/首都/人口等）
CREATE TABLE polity_asset (
  polity_key VARCHAR(255) PRIMARY KEY,
  flag TEXT, flag_svg TEXT, capital VARCHAR(128),
  population BIGINT, area_km2 DOUBLE PRECISION,
  currencies JSONB, languages JSONB, cca2 CHAR(2), cca3 CHAR(3),
  name_official VARCHAR(255), name_zh VARCHAR(255), continent VARCHAR(64)
);

-- 政区描述（含中英文摘要）
CREATE TABLE polity_description (
  polity_key VARCHAR(255) PRIMARY KEY,
  name VARCHAR(255), from_year INT, to_year INT,
  zh_title VARCHAR(255), zh_extract TEXT, zh_thumbnail TEXT,
  en_title VARCHAR(255), en_extract TEXT, en_thumbnail TEXT
);

-- 历史人物
CREATE TABLE person (
  id BIGSERIAL PRIMARY KEY,
  person_id VARCHAR(128) UNIQUE NOT NULL,
  name VARCHAR(128), name_en VARCHAR(128),
  birth INT, death INT,
  nationality VARCHAR(128), era VARCHAR(64),
  total_points INT
);

-- 人物轨迹点
CREATE TABLE person_point (
  id BIGSERIAL PRIMARY KEY, person_id VARCHAR(128) REFERENCES person(person_id),
  seq INT, year INT, place VARCHAR(255),
  lng DOUBLE PRECISION, lat DOUBLE PRECISION,
  intro TEXT, works JSONB, related JSONB, context TEXT
);
CREATE INDEX idx_pp_person ON person_point(person_id, seq);

-- 战争
CREATE TABLE war (
  id BIGSERIAL PRIMARY KEY,
  war_id VARCHAR(128) UNIQUE NOT NULL,
  name VARCHAR(255), name_en VARCHAR(255),
  start_year INT, end_year INT,
  type VARCHAR(64), category VARCHAR(64),
  tags JSONB, summary TEXT, total_battles INT
);

-- 战役
CREATE TABLE battle (
  id BIGSERIAL PRIMARY KEY, war_id VARCHAR(128) REFERENCES war(war_id),
  name VARCHAR(255), year INT, geom GEOMETRY(Point, 4326),
  belligerents JSONB, description TEXT, outcome TEXT
);
CREATE INDEX idx_battle_geom ON battle USING GIST(geom);

-- 数据溯源（UGC 预留）
CREATE TABLE revision (
  id BIGSERIAL PRIMARY KEY,
  entity_type VARCHAR(32), entity_id VARCHAR(128),
  version INT, payload JSONB, diff JSONB,
  operator VARCHAR(64), status VARCHAR(16), created_at TIMESTAMPTZ DEFAULT now()
);
```

## 5. 业务扩展规划

> 判断标准：是否服务于"横向对比"这一主旨，以及是否能用现有数据资产低成本实现。

### 5.1 第一优先（直接强化核心主旨）

#### 5.1.1 同期世界横向对比台

- **做什么**：锁定一个年份，把全球划分为若干区域（东亚 / 南亚 / 中东 / 欧洲 / 非洲 / 美洲），并列展示各区域当时的政权、重大事件、人口与技术水平。
- **价值**：这就是产品定位本身。目前只有"单点浏览"，没有"横向可比"。
- **实现**：`/api/compare` + 一个新的 `CompareBoard` 组件 + 侧栏分屏。政区数据已足够支撑（Cliopatria 覆盖 15690 个政区）。
- **依赖**：政区数据入库 + 空间查询。

#### 5.1.2 双年份对比（时间纵切）

- **做什么**：同屏左右两个地球（或卷帘式），左边年份 A、右边年级 B，拖动联动或独立。
- **价值**：看"同一片土地在两个时代的样子"，是最直觉的历史教育场景。
- **实现**：两个 `CesiumService` 实例或同一 Viewer 的双相机视口。
- **依赖**：渲染层必须完成 Primitive / MVT 改造，否则双份 Entity 必崩。

#### 5.1.3 全局搜索（Ctrl+K）

- **做什么**：一次检索事件、人物、政区、战争，结果带时空定位，回车即飞往。
- **价值**：当前只能靠拖时间轴"碰运气"，检索是刚需。
- **实现**：PostgreSQL 全文索引 + `pg_trgm` 模糊匹配；前端命令面板组件。
- **依赖**：数据入库。

#### 5.1.4 数据溯源面板

- **做什么**：事件详情增加"来源与可信度"区，展示史料清单（名称 / 类型 / 是否同时代）、可信度评级、史学争议说明。
- **价值**：**现有数据里 `sources` / `certainty` / `certainty_note` / `historiographic_note` / `disconfirming_evidence` 字段全都有，但界面上一个字都没显示**。零数据成本，直接提升学术可信度。
- **实现**：纯前端 + 详情接口。
- **依赖**：无。**性价比最高的一个**。

#### 5.1.5 事件关联网络

- **做什么**：数据里已有 `graph_edges`（from / to / relation / note），把它可视化为事件之间的因果与关联网络。
- **价值**：从"孤立事件"升级为"事件之间有关系"，这是历史理解的核心。
- **实现**：PostgreSQL 邻接表 + 前端力导向图（可用轻量的 d3-force 或自绘 Canvas）。
- **依赖**：`graph_edges` 入库。

### 5.2 第二优先（内容纵深）

#### 5.2.1 古地图卷帘对比

- **做什么**：叠加历史地图影像（如 1880 年的世界地图），用卷帘滑块对比"当时人眼中的世界"与"现代底图"。
- **价值**：视觉冲击力最强，且能把"历史地图"这一独立内容品类纳入。
- **实现**：Cesium 的 `ImageryLayer` + `SplitDirection`，天然支持分屏卷帘。
- **依赖**：需要获取并地理配准历史地图瓦片（见 6.3）。

#### 5.2.2 战争进程逐日回放

- **做什么**：选定战争，按时间推进战线与战役位置，类似纪录片里的动态形势图。
- **价值**：`wars/` 已有 89 个战争档案与 850 个战斗记录，是现成的叙事素材。
- **实现**：战役时间线 + 地图动画；前端按 `timeline` 字段逐帧推进。
- **依赖**：补齐 7 个缺失战争 + 修复 `index.json` 引号损坏。

#### 5.2.3 人物轨迹剧场

### 6.6 政区几何简化：实测结果

**问题**：Cliopatria 导出的坐标精度最高达 33 位小数（约亚微米级），单个世纪文件顶点数百万。`polities_1900_2000.json` 原始 38.87 MB，即使 gzip 也有 11.20 MB，是项目最大的性能瓶颈，也是此前"政区只渲染 800 个"的根因。

**诊断**：65% 的顶点集中在直径 ≥10° 的大陆环中；相邻坐标呈 0.1° 量级的"台阶状"，说明上游是栅格矢量化产物。因此**固定绝对容差几乎无效**（首轮只删掉 1.6% 顶点），必须让容差随环尺寸缩放——这是本项目最容易踩空的一个技术判断。

**方案**：`scripts/data/simplify-polities.mjs`
1. Douglas-Peucker，容差 = 环对角线 × 8%，夹在 0.002°–0.12°（约 220 m – 13 km）
2. 坐标量化到 4 位小数（约 11 m），并去除量化产生的重复点
3. 剔除 < 4 点的退化环与空要素
4. 只保留 UI 实际读取的字段：Name / FromYear / ToYear / Area / Type / Wikipedia
5. 同步产出 `.gz`，供 nginx `gzip_static` 直接下发
6. 依输出重建 `index.json`

**实测（55 个文件）**

| 指标 | 原始 | 简化后 | 降幅 |
|------|------|--------|------|
| 总体积 | 183.6 MB | 52.4 MB | **-71.5%** |
| 预压缩体积 | — | 13.8 MB | — |
| 顶点数 | 4,812,887 | 2,787,832 | **-42.1%** |
| 最大单文件 | 38.87 MB | 10.93 MB | **-72%** |
| 要素丢失 | — | 0 | 无 |

结构校验覆盖 167,016 个环：环闭合、最小点数、坐标有限性、经纬度范围、几何类型、名称完整性 —— **全部通过**。

**回滚路径**：原始文件完整归档在 `data/polities-original/`。提高精度只需调参重跑：

```bash
TOL_REL=0.04 TOL_MAX=0.05 node scripts/data/simplify-polities.mjs --commit
```

**同时完成的清理**：`public/` 中 5 个备份文件（合计 87 MB，原本会随构建上传到生产）已移入 `data/backups/`；`vite.config.js` 新增 `stripNonShippable` 构建期防线，确保原始 dump 与备份文件永不进入 `dist/`。

**仍未解决**：单个世纪文件 10.93 MB 对移动端仍偏大。彻底解决需要矢量瓦片（tippecanoe）+ 视口按需加载，属 Phase 3 范围。

### 6.7 数据校验与修复

**问题**：`public/` 的数据由十来个一次性脚本长期拼装而成，从未有机制检查其一致性。缺陷要到运行期才暴露，且往往表现为"某个年份莫名空白"这类难以归因的现象。

**工具**（**零新增依赖**——本环境的 npm registry 无法解析部分传递依赖，`mapshaper` 因此安装失败，故校验器手写）：

| 脚本 | 用途 |
|------|------|
| `scripts/data/validate-data.mjs` | 全量校验：事件（中/英）、战争、人物、政区（含几何）、参考数据；发现 ERROR 时以退出码 1 中断构建 |
| `scripts/data/repair-data.mjs` | 修复取值无歧义的机械缺陷，默认试运行，`--commit` 才写入 |

命令行入口：`npm run validate:data` / `npm run repair:data`，并已挂到 `prebuild`——**数据不合格则构建失败**。

**校验发现的真实问题与处置**

| 发现 | 判定 | 处置 |
|------|------|------|
| 战争索引 `index[3]` 为空壳 `{"tags":{},"totalBattles":0}` | 缺陷 | 移除（89 → 88），索引与磁盘档案恢复一一对应 |
| 31 处 `coordinates_approx` 存的是字符串 `"null"` | 缺陷（中英各 31 处，完全对称） | 改为真正的 JSON null |
| `events/` 下 10 个无后缀残留文件（`-1895` … `-1904`） | 过时草稿：与 `.json` 副本内容不同且更短 | 归档至 `data/backups/events-orphans/` |
| `"47.64, 225.77"`、`"-69.27, 279.70"` | **非地球坐标**：前者是海盗2号在火星乌托邦平原的着陆点（火星用 0-360 经度），后者是 SN 1987A 的赤纬 | 标记为"无地球坐标"；**刻意不做经度归一化**——把 225.77 归一成 -134.23 会把火星着陆点放进加拿大 |
| 550 个年份 `events` 为空 | **非缺陷**：302 个在公元前 2000 年以前，最晚 372 年，≥1000 年一个都没有，属数据源本身稀疏 | 保留；校验器改为仅在近代出现空年份时才报错 |
| 负年份的 `year_label` 比 `year` 大 1（year -1895 → "公元前1896年"；偏移 +1 计 673 个，偏移 0 计 2527 个） | 数据语义问题，两种纪年约定都存在，哪一个权威需人工判断 | **仅记录不修改** |

最后两条是**刻意"不修"**的。校验器的价值不只是自动改，更是把"需要人判断"的事明确标出来——静默改写数据比留着问题更危险。

**结果**：`ERROR 0 / WARNING 0`，全量校验耗时 6.3 秒。
